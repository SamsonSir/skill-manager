# 内部写作模块

## 账号隔离
每次显式绑定用户指定的账号项目，读取其 AGENTS.md、账号配置.md、人物定稿、语气样本及当前进度。账号不明且存在多个候选才询问，不能默认沿用上一账号。人物、受众、语气、选题范围、视觉、事实和权限均来自当前账号配置；缺失就标明，不回退为素琴或其他账号。所有输出存入当前账号项目。不同账号不共享未经授权的私有素材。

## 正文执行模型

所有文章正文与标题执行主入口 `SKILL.md` 的“通用正文与标题模型路由”：优先Gemini-API网页版3.8 Flash中等，失败由当前Agent使用本模块和账号专属规则接续，不再默认调用Gemini CLI。模型不替代素材准备、事实核对和最终验收。

## 方法
开始写作前按 [账号内反馈与样文](../feedback-learning.md) 读取当前账号、当前文体的反馈和样文；主入口已读取且记录未变化时复用结果。只应用相关有效经验，候选不当硬约束，样文不当人物事实。用户给出有复用价值的改稿反馈后按该协议登记，不另开学习流程或让用户维护文件。

读取当前账号的角色创作合同、人物定稿、语气锚点和近期已认可正文，先写一份本篇“可用素材清单”：事实来源、可写人物事实、只能表达的观点、明确缺失项。角色创作合同缺失时停止，不以模型对角色的印象继续。提炼语气、立场、具体程度与节奏；不要套其他作者 my-voice 文件。借鉴 gzh-short-post 的聚焦、具体与自然收尾，以及 gzh-longform-writer 的素材核对；不继承其固定字数、你字限额、科技表达或只有两种骨架的限制。
可调用 human-writing 做材料充足度、说话位置和自然中文检查：现实稿先确认事实、动作、原话与判断是否足以支撑篇幅；材料不足时补研究、缩小题目或明确缺口，不用抽象道理灌字数，不把创作的例子包装成亲历；一般观察或明确条件情境可使用符合生活逻辑的例子。每个主要段落应增加新信息、动作、关系变化或具体感受。
事实与文学创作分开；没有素材不能包装为亲历。事实类型由句子是否声称真实发生决定。自述“我昨天去过”、真实人物履历、真实对话/引语及可核外部事实需来源；“有时候睡醒晚了，吃碗热面再出门”这类一般观察、建议或条件情境可以创作，不因动作和物件具体就判成亲历。明确真实指向的句子不能靠换成第二人称或把 type 标为 general_observation 绕过来源。

素材不足时按当前账号已有素材策略处理，不把“普遍观察＋观点”固定为替代文体。不要把具体场景改成泛泛物件罗列，再用多段道理补足篇幅。没有材料支撑的真实经历不能伪造，但事实核对不要求压低情绪、删除人物偏好或改变已确认的账号类型。用户已认可正文保留原版，修改另存版本。
材料决定开头、发展与结尾，不强加冲突、金句或释然。写后以 humanizer 等作为局部检查，去空话和机械转折，不能为了去AI味加虚构细节或改作者立场。
human-writing 的标点禁令、固定材料数量和通用长帖口吻不是账号规则。当前账号的人物定稿、认可样文、篇幅与文体优先；通用 Skill 只提供检查维度，不能覆盖角色声音。
完成正文后不要直接宣告通过。只看最终稿，重新提取第一人称经历、履历、对话、引语和外部事实，写入工作流规定的 `正文事实账本.json`；与素材清单逐项比对。再写 `角色风格验收.json`，逐项引用正文证据，对照角色合同、认可样文和近期成稿检查立场、说话位置、具体程度、节奏、收尾和结构重复。任何无来源具体亲历都必须删除、改为不指向人物亲历的观察，或在账号合同允许并已确认公开呈现方式时明确作为虚构。交付正文、两份验收文件、简短事实缺口及检查结果；检查是否符合当前读者、一个中心、人物/时间线一致、标题兑现、无重复套话与不当承诺。不能声称任意模型完全复制语气。

## 写作与改稿验收（2026-09-17修订）
写前必读账号配置中的“文风执行参照”（如有），包括认可样文和失败对照。角色立场、语气与内容范围沿用已确认基线，不因单篇失败重新询问账号定位。
本篇开始前在内容卡用简短文字说明：写哪件事；人物对此有什么具体感受、需要或选择；读者可能在哪一点认出自己。情绪强弱服从题材，不强塞孤独、心动、释然，也不把情感账号写成纯生活说明或读书说理。

初稿完成后合并审读一次，再填验收；有实质问题才改稿，已满足要求的好句和段落保留。检查：
- 标题给出的阅读理由是否被正文兑现；读完留下本篇特有的感受、观察或态度。
- 各段是否有推进，后半段有无换词重复和通用劝慰；确实难判断时再做段落摘要，不把逐段摘要、压命题和寻找反例设为每篇必交材料。
- 情绪是否由可感的行为、选择、语气或观察承载；情绪强弱服从题材，不要求每篇冲突、提问、反转或金句。
- 单独检查常用词序、修饰关系和指代。像“话说的人”误写“说话的人”这类词序错误须按语境纠正，不能因整段读着顺就漏过；“话说”本身不是禁词。一般读者能否直接理解句子与段落之间的关系，不能只按作者意图判清楚。
- 事实与说话位置是否正确；对照账号依据和近期实际正文，看推进是否机械重复，不仅比较题材或段数。
- 结尾是否回到这篇的事，语言是否自然，断言是否超过素材支持。

内容卡用简短一段记录具体借鉴的方法、发现的问题和修改（无需修改则如实写），不再叠加独立审查表。事实账本与风格JSON是同轮审读的机器记录：按最终稿一次写入，哈希由工具计算；六个维度是检查角度，不是六轮审稿。各项证据须对应实际正文和已读来源，不复制一段泛泛“符合底座”填满所有项。

有具体问题才退回，不因措辞偏好无限返工。尚未解决的问题保留为待修订，不伪称通过。脚本只校验结构和部分线索，不能证明文风合格、读者喜爱或运营效果；跨Agent稳定性须实际执行验证。
