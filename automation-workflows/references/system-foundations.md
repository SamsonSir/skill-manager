# 企业系统地基：实施与验收

按当前流程需要选择能力，不默认建设全公司平台。

| 能力 | 需要落实 | 可观察的验收 |
|---|---|---|
| 业务与数据语义 | 实际流程、完成标准、数据字典、规则来源与版本、稳定标识 | 同一业务样例得到一致解释；冲突信息有确定的权威来源 |
| 身份与权限 | 人员与系统账号映射；服务端按对象和动作校验；凭据受控保存 | 越权操作被拒绝；撤权后不能继续访问；不同用户上下文不串用 |
| 业务工具 | 输入输出、前置条件、写入副作用、错误类别、执行凭证 | 正常与失败输出均可解释；技术错误不覆盖业务状态 |
| 状态与重试 | 持久化任务状态、请求标识、去重；结果未知时先查状态 | 重复事件不重复建单；超时后可核对真实结果 |
| 人工与恢复 | 接管人、已执行步骤、日志关联、必要备份与回退 | 部分完成能定位并接管；备份能实际恢复，而非仅存在文件 |

## 改造已有系统

先跟业务人员走一笔真实正常流程和相关异常，找系统管理员或原厂商核对接口、权限、数据和维护边界。将缺口分成已有可用、已有但不可访问、需要补建。先通过数据字典、接口映射或适配层复用能力；只有明确限制才论证数据库迁移或重构。

没有接口时先核对厂商支持或受控导入导出。使用 UI 自动化需说明依赖和失败检测，不能把操作页面成功等同于后端接口稳定。对照运行时明确哪一方有写权限，避免新旧流程重复执行同一业务动作。

## 新建系统

先定义一个业务闭环的正常与失败结果，再设计角色、数据、状态转换和工具约定。实现包含读取、写入、查询状态和异常处理的最小完整流程，然后接入 Agent。按实际影响验收权限、重复请求、超时、人工接管及恢复，再扩大使用范围。

## AI 资产与开发治理的边界

聊天内容、提示词、业务知识与正式制度用途不同。复用前明确负责人、来源、有效版本、适用对象和访问范围；不要默认汇总员工全部聊天作为共享知识。

AEG 等开发治理负责约束开发过程和验收证据；业务运行时仍需实现身份、工具、状态和恢复。遵守规范、连接模型或完成 Demo，都不能单独证明系统已可生产。
