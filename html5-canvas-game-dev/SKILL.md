# HTML5 Canvas 小游戏开发与自动验证

## 何时用

用户要"生成一个 XX 小游戏"、跑酷/躲避/街机玩法，或要求在微信/浏览器里直接能玩。
默认产出**单文件 HTML5 游戏**（零依赖、离线可玩、可直接丢进微信浏览器、可用 web-view 嵌进小程序）。

**不要**一上来就问"要小程序还是网页"——先做 H5 版（立刻能玩能预览），交付后再问是否要移植成原生微信小游戏。
原生微信小游戏需要微信开发者工具预览，且无 DOM（`wx.createCanvas()`），UI 层要全部改画在 canvas 上，属于独立工作量，不要顺手一起做。

## 硬性约定

- **单文件**：`index.html` 内联 CSS + JS，不引外部资源、不引 CDN、不加载图片/音频文件。
  美术全部用 Canvas 2D 程序化绘制（路径、渐变、粒子），音效用 Web Audio 合成。
- **移动优先竖屏**：`viewport` 加 `maximum-scale=1,user-scalable=no,viewport-fit=cover`；
  CSS 全局 `touch-action:none; overscroll-behavior:none; user-select:none`。
- **横屏（桌面）加手机画框**：`innerWidth > innerHeight*1.15` 时把舞台设成 9:16 居中 + 圆角，
  比拉伸铺满好看得多。见下方 `layout()` 模板。
- **DPR 适配**：`Math.min(devicePixelRatio, 2)`，`ctx.setTransform(DPR,0,0,DPR,0,0)`，逻辑坐标用 CSS px。
- **固定步长更新**：累加器 + `1/60` 步长 + 单帧最多 5 步 + `dt>0.25` 截断（切后台回来会大跳）。
- **切后台自动暂停**：监听 `visibilitychange` 和 `blur`。
- **尺寸全部相对屏幕高 H**：定义 `CH = H * 0.118`（角色身高）做基准，障碍物/字体/间距都以 CH 或 H 为单位，
  否则换个机型就穿模或错位。

## 跑酷玩法数值必须先算，不能凭感觉

**最容易翻车的地方**：障碍物太宽 + 初速太低 → 跳跃滞空距离不足以越过障碍 → 关卡在数学上不可能通过。

先定跳跃参数，再反推障碍宽度：

```
v0 = 1.25 * H        // 起跳速度
g  = 3.40 * H        // 重力
滞空时长 T_all = 2*v0/g = 0.735s        // 与 H 无关，纯常数
跳跃高度 apex = v0²/(2g) = 0.230 * H    // 约 2 个身位
```

角色在高度 h 之上的停留时长：

```
T(h) = 2 * sqrt(v0² - 2*g*h) / g
```

**可越过条件**（`Wb` = 障碍碰撞盒宽，`Pw` = 角色碰撞盒宽）：

```
worldSpeed >= (Wb + Pw) / T(h)
```

- 算出每个障碍的临界速度后，取所有障碍里最大的那个，作为**初速下限**，再留 20% 余量。
- **连跳约束**：障碍间距时间必须 > 滞空时长 + 反应时间。
- **深坑**别用矩形碰撞（会误判边缘），改用"落到地面线以下 X 像素"判定，手感更宽容。
  坑的危险窗口 = `0.8 * 坑宽 / 速度`，必须明显小于滞空时长。
- 提速会**降低**越过难度（滞空时水平位移变长），所以难度增长靠"间距时间变短"而不是"障碍变宽"。

### 但"能不能跳过去"是伪命题——真正卡人的是**起跳时机窗口**

上一条只保证「跳得够远」，不保证「有机会跳」。玩家必须在正确的**那一小段时间**里按下跳，
这个窗口才是手感的全部。推导后会发现它**与跳跃力、初速、重力全都无关**：

```
起跳窗口(px) = 障碍间距 - (障碍宽 + 角色宽)
起跳窗口(ms) = 起跳窗口(px) / 跑速 * 1000
```

理由：跳得越用力，滞空越长，水平位移也越长，你和下一个障碍的关系**等比例**变差，正好抵消。

**所以调跳跃参数永远救不了间距太密的问题，只能拉开间距。**

| 间距(H=844,W=390) | 起跳窗口 | 手感 |
|---|---|---|
| 113px | 109ms | 人类基本按不出来（本项目第一版就是这个值，机器人每关必掉 1 血） |
| 151px | 184ms | 偏难，适合最高难度 |
| 226px | 419ms | 舒服 |
| 300px+ | 690ms+ | 很宽松 |

**障碍数量要按窗口反算，不要写死**：

```js
var need = 最宽障碍 * H + L.PW + W * winFrac;   // winFrac = 想要的窗口占屏宽比例
var n = d.per;
while (n > 2 && band / (n - 1) < need) n--;     // 摆不下就自动减
```

这样**永远不会连成一堵跳不过去的墙**。另外必须校验"相邻障碍合并成团"的情况：
两个障碍挨得比角色宽还近时，等于一个超宽障碍，要按团宽重算可跳性。

### 多圈上升塔（螺旋坡道）的三个几何陷阱

"一圈一圈往上爬"的塔很好玩，但有三个坑，每一个都能让关卡在数学上不可能通过：

1. **上下两关在 x 上是完全重叠的**，所以碰撞判定必须按关号过滤：
   `if (ob.f !== P.floor) continue;`
   否则上层那排洗衣机就会"隔空砸到"下层正走过的玩家。这个 bug 的现象非常像手感问题
   （每关固定掉 1 血、位置固定），极难靠看截图发现。

2. **坡道会让头顶净空在拐弯处归零**。如果每一关是从头到尾的连续斜坡，
   两关之间的净空在拐角降到 0，上层任何障碍都会插进下层玩家身上。
   **解法：每一关做成「平坦台子 + 结尾一小段斜坡」**（`RAMP_T ≈ 0.16`），
   台子段净空恒为 `FH`，只有最后一段斜坡收紧。
   这同时也符合"跳完 N 个障碍就到一个台子"的直觉设计。

   ```js
   function surfZ(f, x) {
     var t = clamp((x - f.xa) / (f.xb - f.xa), 0, 1);
     var e = clamp((t - (1 - RAMP)) / RAMP, 0, 1);   // 前段平、末段爬坡
     return f.k * L.FH + e * L.FH;
   }
   ```

3. **胜利判定要检查"真的走得到"**。顶层如果只剩一小段斜坡，
   玩家必须贴到犄角才够高，判定阈值就形同虚设。
   反解一下：`需要的 x` 必须比"角色能走到的最远 x"留出几十像素余量
   （最远 x 通常是 `XR - PW*0.18` 这类夹取值）。
   最简单的解法是**给顶层单独加长斜坡**（`f.ramp = 0.42`），顺便也更好看。

### 先写离线仿真，再改游戏参数

调数值时**别用无头浏览器一遍遍试**（一轮 30s~5min，看不到原因）。
先用 Python 把 `updRun` 的支撑/碰撞逻辑**逐行照抄**成 60fps 仿真，让一个机器人跑完整关，
统计"掉血次数 / 通关率 / 最差起跳窗口"。这样一轮只要 1 秒，可以扫描几十组参数。

仿真的价值在于**能把"受伤原因 + 受伤前 40 帧"打出来**；把这三条一起看，问题会自己浮现：

```
受伤记录: 撞上了洗衣机 t=1.25 x=-37 z=0 fl=0
```

从 `z=0`（贴地）+ `fl=0`（关号对）+ 位置固定在同一个 x → 一眼看出
"玩家落在障碍正中间"而不是"跳早了/跳晚了"。

**仿真必须和游戏同源**，尤其注意两处极易写错的顺序问题：

- `wasGround` 要在**按键处理之后**采样。游戏里 `pJump()` 先于 `updRun` 执行，
  所以跳跃那帧 `wasGround` 已经是 `false`；仿真里若在跳跃前采样，
  落地判定会立刻把玩家按回地面，表现为"原地无限兔跳、跳跃数上千"。
- 速度积分写 `P.vx += (target - P.vx) * min(1, acc*dt)`，
  漏掉 `min(1, ...)` 会让加速度变成 `acc*dt`，玩家慢如蜗牛、永远撞在第一个障碍上。

### 手感兜底：土狼时间 + 跳跃缓冲

任何跑酷都建议加上，成本极低：

```js
L.COY = 0.11;   // 离开地面后 0.11s 内按跳，仍然算数
L.BUF = 0.16;   // 落地前 0.16s 抢按，落地瞬间自动兑现
```

`doJump()` 里要 `P.coyote = 0` 消费掉，否则会变成"隐形二段跳"。


## 换装 / 捏人 / 角色展示类（非动作玩法）

这类游戏的核心不是数值而是**美术与即时反馈**，重点完全不同：

- **角色用"单位坐标系"画**：定义 `eggPath()` 之类的轮廓，底在 `y=0`、顶在 `y=-1`（或 -0.9）。
  所有衣服/帽子/配饰的坐标都写成这个单位系的常量，渲染时 `ctx.translate(x, floorY); ctx.scale(s, s)` 即可。
  好处：主舞台、衣柜缩略图、导出图片**共用同一个绘制函数**，改一处三处同步。
- **Q 弹动画 = 绕脚下缩放**：`ctx.scale(s*sx, s*sy)` 且原点就在脚底，压扁时脚不动。
  落地给 `sy=0.78, sx=1.22`，起跳给 `sy=1.17, sx=0.87`，每帧 `sy += (1-sy)*13*dt` 回弹。裸写关键帧做不出这个手感。
- **装扮做成"数据表 + 绘制函数"**：`[{id,name,draw(g,lk)}]`，一分类一个数组。
  需要"画在衣服外层"的单品（背带裤/背带裙）加个 `over:1` 标记，绘制顺序里排在上衣后面。
- **身体分区先定死再画衣服**：例如脸在 `-0.50` 以上、上衣 `-0.50~-0.20`、裤子 `-0.26~0.04`。
  **衣服下摆只要越界一点点，就会把裤子整条盖住**（T 恤画到 +0.06 时，蓝蛋仔直接变成全白蛋）。
- **衣柜缩略图 = 小 canvas 画同一个角色**：每次切分类只渲染当前分类（≤8 个），
  每张缩略图用"当前 look 换掉这一件"来画，用户一眼就能看出穿上是什么样。
- 缩略图里的高帽子要单独缩小 `u`，否则会顶出画布：`it.tall ? h*0.58 : h*0.76`。
- 换装页的衣柜做成**底部抽屉**（`translateY` 过渡 + `flex-wrap` 的分类标签），
  比弹出模态框在手机上顺手得多；标签超过 4~5 个一定要 `flex-wrap`，横滑用户看不见最后一个。

### 圆球/蛋形角色的衣服必须"贴球面"画（这一节是换装类的真正地基）

只要角色是"圆球/胖蛋"这类**没有任何直边**的造型，衣服就**绝对不能**用矩形或梯形。
用了的结果：一穿上，圆球立刻被切成方的 —— 而"圆圆的一颗"恰恰是这个角色的全部魅力。

**第一步：把轮廓采样成「y → 水平半宽」查表。**
把轮廓右侧（一半）的贝塞尔逐段采样 160 点，存成 `[y, |x|]` 并按 y 排序，
查表用二分 + lerp。这张表（下面叫 `eggHW(y)`）是**所有衣服的唯一依据**。

```js
var HW = (function () {
  var pts = [], N = 160;
  function seg(p0, p1, p2, p3) {                 /* p 都是 [x, y] */
    for (var i = (pts.length ? 1 : 0); i <= N; i++) {
      var t = i / N, u = 1 - t;
      var x = u*u*u*p0[0] + 3*u*u*t*p1[0] + 3*u*t*t*p2[0] + t*t*t*p3[0];
      var y = u*u*u*p0[1] + 3*u*u*t*p1[1] + 3*u*t*t*p2[1] + t*t*t*p3[1];
      pts.push([y, Math.abs(x)]);
    }
  }
  seg([0,0], [-0.288,0.010], [-0.50,-0.170], [-0.50,-0.452]);   /* 右下半 → 最宽处 */
  seg([-0.50,-0.452], [-0.50,-0.712], [-0.288,-0.90], [0,-0.90]); /* 右上半 → 头顶 */
  pts.sort(function (a, b) { return a[0] - b[0]; });             /* y 从 -0.90 到 0 */
  return pts;
})();
function eggHW(y) {                       /* 二分 + lerp，越界夹到端点 */
  var p = HW, n = p.length;
  if (y <= p[0][0]) return p[0][1];
  if (y >= p[n-1][0]) return p[n-1][1];
  var lo = 0, hi = n - 1;
  while (hi - lo > 1) { var m = (lo+hi)>>1; if (p[m][0] <= y) lo = m; else hi = m; }
  var d = p[hi][0] - p[lo][0];
  return lerp(p[lo][1], p[hi][1], d > 1e-9 ? (y - p[lo][0]) / d : 0);
}
```

**第二步：五把刷子，覆盖所有衣服形状。** 全部左右边界都取自 `eggHW`。

| 刷子 | 用途 | 形状 |
|---|---|---|
| `eggHug(g, yTop, yBot, padTop, padBot, N)` | 抹胸 / 项圈 / 毛领 / 肩披 | 上下边水平，左右贴壳；`pad` 可上小下大做喇叭口 |
| `eggSkirt(g, yTop, yBot, hem, waves, amp, bow)` | 裙 / 袍 / 长外套 | 上边贴壳，往下外扩到 `hem`；`waves>0` 波浪下摆，`bow>0` 下摆中间往下鼓一点 |
| `eggHem(g, yBot, hem, waves, amp, bow)` | 只描下摆一条边（金边 / 蕾丝 / 毛边） | **参数必须与对应 `eggSkirt` 完全一致**，否则金边会漂到裙外 |
| `skirtBand(g, yTop, yBot, hem, ya, yb, pad, N)` | 腰带 / 胸甲 / 腰封 | 跟着**袍子外扩后的**轮廓取半宽 |
| `domeBand(g, hw, yTop, yBot, N)` | 冠的底环 / 横着箍在脑袋上的条 | 上下边都跟着球面弯（`domeDrop(x)=0.62x²`） |

**外扩曲线是全文最要害的一行。**

```js
function skirtW(yTop, yBot, hem, yy) {
  var t = clamp((yy - yTop) / (yBot - yTop), 0, 1);
  return Math.max(eggHW(yy), lerp(eggHW(yTop), hem, t * t));   /* ← 必须是 t² */
}
```

- **绝对不要用 `smoothstep`（`t*t*(3-2t)`）**：它在 `t=1` 处斜率归零 →
  左右两条侧边最后变成**垂直线**，接上一条水平下摆，袍子就是一个 **90° 直角的方法板**。
  这个坑一次能同时毁掉 3~5 套衣服，而且**不报错、不溢出，只是悄悄变丑**。
- 用 **`t²`**：斜率在下摆处最大，"最宽处"正好落在下摆上，方角变钝角，轮廓才是钟形。
- **下摆外扩量必须 > 0.09**（相对蛋壳最宽处）。外扩只有 0.04 时**什么曲线都是直筒**
  —— 因为 `max(eggHW, 外扩)` 里蛋壳本身太宽。

**量化判据**（直接写成断言，别靠眼睛）：
量"下摆上方 12% 高度处"的 `skirtW` 斜率 —— `smoothstep` ≈ 0.13~0.22，`t²` ≈ 0.38~0.65，
**阈值取 0.25** 能干净地把两者分开。顺手也断言 `skirtW(下摆) - skirtW(上边) > 0.09`。
为此把 `eggHW` / `skirtW` 也挂进 `?debug=1` 的调试钩子（见下节）。

**第三步：配套的三条规矩。**

1. **腰带 / 胸甲用 `skirtBand`，不要用 `eggHug`。**
   用 `eggHug` 时袍子一下摆外扩，腰带就缩进袍子里面，变成一条漂在布料上的短线。
2. **衣服画完统一罩一层球面光照**（`ballShade`：radial 高光 + 右侧暗面 + 下缘暗面）。
   不罩的话，一件平涂的袍子会把球变成一张平面的纸。**只穿衣服时罩，光着不罩**
   （裸露的壳自带高光已经够了，再叠会脏）。**袍脚压暗只能用渐变** ——
   硬边 `fillRect` 会在袍子上横切出一条明显的色差带。
3. **背饰做成 `back` + `front` 两段，一件背饰画两遍。**
   `look` 里通常只有一个 `back` 槽位，但"立领（要长在身体之后）+ 肩披（要压在袍子上）"
   这种组合没法拆成两件可选品。让一件背饰同时有：
   - `back(g,lk,st)` —— 身体之前那一遍：翅膀 / 拖地披风 / 立领；
   - `front(g,lk,st)` —— 衣服之上那一遍：肩披 / 毛领。

   `paintEgg` 里两遍分别调用。**反例**：王后的立领原来整件都画在 `front` 那一遍，
   结果两片大白立领悬在脑袋两侧，像一对翅膀，第一眼像渲染坏了。

**绘制顺序模板**（`paintEgg`）：
`back.back → 蛋身(壳+球面高光) → 裤子(非over) → 上衣 → 裤子(over) → 裙 → ballShade → back.front → 脚 → 手臂 → 腮红/眼/嘴/眼镜/帽`

**第四步：几个必踩的美术坑。**

- **白珍珠 / 白毛边落在浅色背景上会整个消失** → 必须描一圈淡金或淡灰（`rgba(190,158,102,0.55)`）。
  同理"低透明度 ≠ 高亮"，要亮就得两层叠或上 `createRadialGradient`。
- **上衣的上缘不能开得太高，否则"球"就没了。** 圆球角色的**唯一"圆"的锚点就是头顶露出的那一段壳**。
  实测：水手服的领口画到 `y=-0.74`（蛋身高度的 82% 处）、雨衣本体画到 `-0.70` 还叠了一圈
  `-0.88~-0.66` 的帽子 —— 两件都把上半只蛋罩死，远看是一摞横条 / **一个黄色油桶**，
  圆滚滚的轮廓整个丢掉（而"圆圆的一颗"恰恰是这个角色的全部魅力）。
  **判据：任何上衣/外套的上缘都不该高过 `-0.62`（约蛋身高度的 70% 处），
  即头顶至少留 25% 的裸壳当锚点。** 收高之后水手服和雨衣立刻就圆回来了，改动只有两个数字。
  另外**"挂在背后的帽子"不要用 `bandPath`**（那会变成一圈箍在头顶的盖子，且跟着球面走＝贴着头），
  改成 `ell()` 画一个压扁的圆坨放在后背（`ell(g,0,-0.58,0.30,0.155)`）才是"脱下来挂着"。
- **手臂的肩点要落在衣服轮廓之外**（本项目 `±0.425`），再加一层深色垫底描边
  （`rgba(24,34,62,0.26)`，线宽比袖子大 0.026）把手臂"从衣服上抠出来"。
  手臂压在胸口时，整条看过去就是两坨深色补丁，还会盖住毛领和肩章。
- **横着箍脑袋的东西（冠的底环、额饰）不能拉成直条**，否则圆脑袋会从它的两侧"从后面冒出来"。
- **多层薄纱/纱裙的层间距要拉开**（本项目 ~0.077）。贴太近时三层半透明白纱会在中间
  叠成 ~88% 不透明的一团白，既看不出层数、又把底色整个盖掉；每层再描一圈有色边才有"层"。
- **缩略图要给大件单独标 `span`**：`paintThumb` 里
  `var span = item.span || (item.apply ? 1.44 : 0.80);`，可见半宽 = `span / 1.72`。
  翅膀/披风/立领用默认 0.80 会被画布直接切掉（本项目终版 `span: 1.45`）。
- 帽子这类"高件"仍然用 `tall:1` 单独缩小 `u`。

**第五步：两套坐标系必须先分清 —— 这是换装里最贵的一次翻车。**

只要蛋壳为了"把腿露出来"被抬高过（本项目：`translate(0,-LEGH)` + `scale(EGG_K, EGG_K)`，
`LEGH=0.118`、`EGG_K=0.869`），那么**衣服和蛋壳共用的是「蛋壳局部系」，
而腿 / 脚 / 鞋 / 地面在「名义系」**，两者差一个仿射：

```
名义 y = -LEGH + EGG_K × 局部 y          （本项目 y 轴向下为正、蛋底为 0）
```

- **衣服之间的相对关系**（"上衣下缘要压过裙腰"）**在局部系里直接比就对**，不用换算。
- **任何和"脚 / 鞋 / 地面"有关的值必须先换算**。本项目给"公主长裙"定裙摆时，
  把"名义 -0.055（脚踝上方）"直接写成了局部值，实际落到名义 **-0.166** ——
  裙摆悬在膝盖，下面露着整条小腿。截图一眼可见，但**代码读起来完全正确**。
- 症状的识别方式：先看**有没有东西该露出来却没露**（鞋 / 脖子 / 手腕），
  再看那个 y 值的**数量级**像不像另一个坐标系的值。
- **像素断言也要标明量的是哪个系**。本项目按局部值去截"名义带"，量出来恒为 0
  —— 断言看着"设计得挺合理"，其实在量一片空气。
  **恒 0 或者两个数完全相等，先怀疑坐标系，再怀疑产品。**

**第六步：上下装是"互相让位"的一对数字。**

下装能露出的高度 = `(上衣下缘) − (下装下摆)`。所以：

- 上衣每往下多画 0.04，裙子就矮一截。本项目「王族礼服」第一版收到 `-0.29`，
  裙子只剩一条窄边，穿起来像"一件上衣下面加了个腰带"；礼服收短到 `-0.33` 之后才有裙子的样子。
- **改任何一个都要回头量另一个**，并且把这对关系写进注释（否则下一个人只会改一半）。
- 反过来，"长裙必须及踝"和"鞋要露出来"是**同一个**几何约束的两面：
  先量出脚占 `[-0.080, +0.004]`、鞋最高到 `-0.108`，再反解裙摆该停在哪（本项目名义 `-0.070`）。
  **先量脚，再定摆**；拍脑袋给个"差不多低"的数，鞋就被整条吞掉了。

**第七步：往衣服上写"字"不要用 `fillText`。**

单位系里整只角色才 0.90 高，字号会小到 0.3 上下 —— 小字号下字体发糊，
而且 canvas 的字体度量在不同平台 / 不同 DPR 下还不一样，截图里时好时坏。
本项目「国王冠」要刻一个「王」：直接按笔画画**三横一竖**四个圆角矩形
（上横窄 0.124 / 中横更窄 0.082 / 下横最宽 0.140 / 一竖贯通），
任何缩放下都清清楚楚，还顺带得到"嵌在一块暗红底牌上"的徽记感。
判据直接写成像素断言：**在底牌那一小块里数两种颜色**
（暗红 `r∈[130,200] g<78 b∈[40,100]` 与浅金 `r>246 g>218 b∈[140,205]`），
两个都够多才算"字真的画出来了"，能一次拦住"没画 / 被后来的层盖掉 / 颜色调成和底牌一样"。

## 追尾视角（伪 3D）跑酷 —— 和横版是两套引擎
需求长这样：「角色背对镜头、直直往前跑」（《蛋仔派对》跑酷那种）。
**不要在横版引擎上改** —— 横版 x 直映屏幕 x，追尾 x 要除以深度，
玩法数值全挂世界坐标，两套投影不能共用。可复用的只有角色轮廓函数和音效合成。

### 投影与相机（三行就够）
```js
var d = z - camZ; if (d < NEARZ) d = NEARZ;   /* 近裁剪，防 d<=0 除爆 */
var s = FOCAL / d;                             /* 每世界单位 = 多少像素 */
return { x: W*0.5 + (x-camX)*s, y: HORIZON + (CAM_UP-y)*s, s: s };
```
- **相机距离必须用「角色占屏宽」反解**：角色宽 1.0 世界单位时
  `占屏宽 = FOCAL/(CAM_BACK*W)`。凭感觉给一定会把镜头贴到角色脸上
  （实测 `CAM_BACK=3.05` → 角色占屏宽 92%）。竖屏要 42% → `CAM_BACK≈5.2`。
- `HORIZON` 决定角色在画面里的高度：脚点屏幕 y ≈ `HORIZON + CAM_UP*FOCAL/CAM_BACK`。
  想让它落在屏幕 2/3 处就反解。**别把角色放在地平线上**，那样看着像浮着。
- 相机横向跟随要留滞后（`camX = lerp(camX, egg.x*0.72, …)`），
  换道时角色才在画面里略微侧移，玩家看得见"我在往哪边挪"。

### 近处的东西必须主动淡出
透视会让「越过角色」的障碍一路放大到糊满整屏 —— 这是几何必然，不是 bug。
在 `o.z < RUN.z - 0.3` 之后开始 fade、1.2~1.5 单位内降到 0，否则画面会很脏。

### 跑道：横条纹在近处会退化成一块纯色板
一条横条纹在近处就能占掉半屏。**改成棋盘格**：先按距离分段、再按道切竖列，
颜色取 `(段号 + 列号) % 2`。分段循环里加
`if (近段屏幕高 - 远段屏幕高 < 0.55px) break;` 防止远处摩尔纹。

### 想填满画面两侧，只能靠「空中的东西」
x 越大投影越往外 —— 跑道两侧 `x=±3.4` 的装饰在 7 单位距离处屏幕坐标已 600+，
完全在 390 宽的屏外。**所以两侧近景根本填不上**；
真正有效的是让气球 / 糖果 / 星星飘在跑道上方，且贴近镜头时也淡出。

### 圆球角色的腿会被壳盖住
圆蛋底部收得太快（`y=0` 处半宽 0，`y=-0.05` 处已经 0.44），
腿放在 `x=±0.17` 永远在壳里。解法：**蛋身整体抬高 `LEGH` 并等比缩小
`EGG_K=(0.90-LEGH)/0.90`**，让「腿+蛋」总高不变 → 碰撞盒完全不用改；
腿画在"抬高之前"那层坐标系里。
### 圆球角色的「翻滚 / 跟头」不能用 cos 压扁 —— 壳体不许动，动的是贴面层

用户说"翻滚要像前滚翻一样，往前走一个跟头"时，第一反应几乎都是
**绕左右轴转 → 二维上就是纵向压扁**：

```js
/* ❌ 看起来天经地义，实际会让角色"消失" */
ctx.transform(1, 0, 0, Math.cos(roll), 0, 0);
```

**这条对圆球角色是错的，而且错得很隐蔽**：`cos` 在 1/4、3/4 处过零，
整只球会**退化成一条零高度的线**——玩家看到蛋仔"消失一下"，那一帧还可能被压到屏幕外。
补一个 `|cos|` 下限只是把「消失」变成「压成一张饼」，仍然不对。

**正确的模型**（先算再写，两分钟的事）：
球绕水平轴转 θ 时，正交投影下的**轮廓半高**是

```
h(θ) = sqrt(a²·cos²θ + b²·sin²θ)      a = 壳体半宽、b = 壳体半高
```

对 `a=0.50, b=0.45` 的蛋壳，`h` 只在 **0.45 ~ 0.50** 之间变 —— **几乎不变**。
直白说：**圆球滚起来，轮廓看着还是那个球**。真正会翻过来的是**贴在球面上的东西**
（四肢、衣服、头饰），它们的投影 y 大致按 `cos θ` 走。

所以拆成两层：

```js
/* 贴面层的纵向翻转矩阵。支点取**球心**（脚底上方 LEGH + EGG_K*0.45），
   取脚底的话翻到一半整只角色会插进地面。
   |ca| 下限 0.20：正好在 1/4、3/4 处那一帧会退化成零高度的线，描边冒毛刺。 */
function rollFlip(g, roll) {
  var ca = Math.cos(roll);
  if (Math.abs(ca) < 0.20) ca = ca < 0 ? -0.20 : 0.20;
  var pv = -(LEGH + EGG_K * 0.45);
  g.transform(1, 0, 0, ca, 0, pv * (1 - ca));
}
```

```js
if (roll) { g.save(); rollFlip(g, roll); }   /* ← 腿：在壳体之前画，天然"转到后面去" */
drawLegs(...);
if (roll) g.restore();

drawShell(...);                              /* ← 壳体：永远照圆画，不参与翻转 */

if (roll) { g.save(); rollFlip(g, roll); }   /* ← 衣服 / 手臂 / 头饰 */
paintWardrobe(...); drawArms(...); drawHat(...);
if (roll) g.restore();
```

关于支点与 `sq` / `bob`：调用点在 `scale(1/sq, sq)`、`translate(0, bob)` **之后**，
但绘制坐标本身就是「脚底 `y=0`、头顶 `y=-0.90`」的名义坐标，`sq`/`bob` 早已作用在坐标系上，
壳体也跟着一起被压 —— **两者天然同步，支点不需要额外换算**。

三条反例，都是实测踩过的：

- **别用 `ctx.rotate(roll)` 代替。** 那是绕**屏幕法线**转，看着像侧手翻 / 原地转圈
  （用户原话就是嫌弃"原地转圈"）。绕左右轴在二维上表现的就是纵向翻转。
- **别在翻滚时额外把手臂收进身体**。试过 `up += sin(roll/2)*0.78`，
  折叠的肩部旋转和纵向翻转互相打架，手臂变成两块立在球两侧的"小旗"，比自然甩着还难看。
  而且不加也本来就对：翻转会把肩点带到正确的一侧，手臂自然就甩出去了。
- **翻到 180° 时，翻起来的裙摆会把翻上去的脚盖住**（腿在壳体之前画、衣服在之后画）。
  这是分层顺序的必然，不是 bug；真前滚翻也只是很短一瞬，别为它加特例。

**别忘了给"不许塌成一条线"写一条像素级回归**（见下节），
光看代码完全正常，只有量画出来的包络才拦得住。

另：`rotate(sa*A)` 是把手臂往身体**内侧**收，向外张要 `rotate(-sa*A)`；
A 转成负数就是举手（跳跃用）。

### 难度：间隔永远是 `speed × reactT`
反应窗口和速度无关，所以障碍间隔必须跟着速度线性放大，
难度只靠收紧 `reactT`（例：1.12s → 0.68s），**不是靠把障碍挤密**。
生成每一行时**最多 2 个障碍（永远留一条空道）**，或者 3 个全是"能跳过的低障碍"——
这是「不存在必死组合」的结构性保证，比事后调数值可靠得多。

### UI 坑（本项目真实踩到）
`transform: scale()` 呼吸动画会让 Playwright 一直重试 click
（判定「元素不稳定」）→ 换 `filter: brightness()`，滤镜不改 boundingBox。
布局断言要**按屏幕坐标排序后再比**，DOM 顺序 ≠ 视觉顺序
（右边那组按钮 DOM 里是「翻滚 跳」，视觉上也是，但左边那组的索引顺序容易写反）。

## 自动验证流程（关键：用无头浏览器跑机器人）

### 1. 找 Chromium 可执行文件

本机 Playwright 的版本号常和已下载的浏览器对不上，直接 `chromium.launch()` 会报
`Executable doesn't exist at .../chromium_headless_shell-XXXX/`。先列出实际存在的版本：

```bash
ls ~/Library/Caches/ms-playwright/
```

然后显式指定：

```js
const EXE = '/Users/<user>/Library/Caches/ms-playwright/chromium_headless_shell-1243/chrome-headless-shell-mac-arm64/chrome-headless-shell';
const browser = await chromium.launch({ executablePath: EXE });
```

跑脚本时把全局 node_modules 挂上：

```bash
NODE_PATH=/Users/<user>/.nvm/versions/node/v22.22.2/lib/node_modules node test.js
```

### 2. 在页面里注入机器人，而不是在 node 侧轮询

`page.evaluate` 往返有延迟，帧级操作必须注入到页面内跑。
**用 `requestAnimationFrame` 递归，不要用 `setInterval(..., 8)`**：
headless shell 里定时器会被限流到 100~200ms，机器人会直接跳过整个起跳窗口，
表现为"每关固定掉 1 血"，让你误以为是游戏数值问题。

```js
await page.evaluate(() => {
  const D = window.__DR__;
  function tick() {
    requestAnimationFrame(tick);
    if (D.state === 3) { D.start(); return; }        // 死了自动重开
    if (D.state !== 1) return;
    const p = D.player; if (p.dead) return;
    const spd = D.speed;
    let air=null, airD=1e9, grd=null, grdD=1e9;
    for (const o of D.obstacles) {
      const d = (o.x - o.w*0.5) - p.x;               // 到障碍前沿的距离
      if (d < -o.w*1.15) continue;
      if (o.kind === 'air') { if (d < airD) { air = o; airD = d; } }
      else                  { if (d < grdD) { grd = o; grdD = d; } }
    }
    if (air && airD < spd*0.14 && p.onGround && !p.sliding) D.slide();
    if (p.sliding && (!air || airD < -air.w*0.9)) D.endSlide();
    if (grd && grdD < spd*0.19 && p.onGround && !p.sliding) D.jump();
  }
  requestAnimationFrame(tick);
});
```

**目标必须只取"前方还没走过的"**：漏掉 `d < -o.w*0.6` 这个下界，
机器人会盯住身后刚跳过的障碍（`td` 变成很负的数），于是**永远不跳**。
这个 bug 的表现是"掉血位置固定在同一个 x"，很容易误判成关卡设计问题。

**机器人卡住时要 dump「受伤前 40 帧」**，比看汇总数字快得多：

```js
buf.push([P.onGround?'grnd':'air', R.t.toFixed(2), Math.round(P.x), 'z'+Math.round(P.z), 'td'+Math.round(td)]);
if (R.hp < prevHp) window.__BUF = buf.slice();
```

一列 `td` 全是负数 → 目标选择错了；`z` 一直等于某关的台面高 → 卡在换层；
`x` 在同一个值来回 → 被障碍挡住。


### 3. 判定"数值是否公平"的量化标准

用 `D.elapsed = 95` 直接快进到满难度，跑 45 秒，统计掉血次数：

| 机器人表现 | 结论 |
|---|---|
| 满难度 45s 内 0 掉血 | 太简单，提速 / 缩短间距 |
| 满难度平均 10~20s 掉 1 血 | **刚好**（帧级机器人无失误余量，真人会更难） |
| 满难度 10s 内死 | 太难，检查上文的临界速度公式 |

**但要先分清"太难"和"几何上过不去"**：如果机器人的掉血位置**固定在同一个 x**、
或者**每关正好掉 1 血**，那不是难度问题，是关卡生成本身在数学上不可通过
（间距太密 / 障碍连成团 / 上下层碰撞没按关号过滤）。这时**不要调难度参数**，
去查上文的几何陷阱。一次合格的关卡生成应当让**帧级机器人在四档难度全部 0 掉血通关**，
难度差异再靠水位速度、断口、特殊障碍、血量这些**正交的杠杆**去拉。

另外记 `elapsed` 与 `dist`，确认速度单位显示合理（跑步类约 5~9 m/s，
即 `distM += adv / (CH * 0.57)`，CH 为人身高像素、约合 1.75m）。

### 3b. 「动作不许塌」这类断言，量**画出来的像素包络**而不是内部变量

姿态类 bug（塌成一条线、翻到屏幕外、缩成 0）看代码永远正常，只有量渲染结果才拦得住。
做法：铺**纯绿 `#00ff00`** 当底色（角色上不可能出现这个颜色），每个角度画一帧，
用 `getImageData` 求非底色像素的包围盒，断言"最扁 / 最高 > 阈值"：

```js
for (let i = 0; i < 24; i++) {
  const roll = (Math.PI * 2) * (i / N);
  g.fillStyle = '#00ff00'; g.fillRect(0, 0, CW, CH);
  g.save(); g.translate(CW / 2, CH - 90); g.scale(SC, SC);
  E.paintEgg(g, plain, { bob: 0, sq: 1, legPh: 0, armPh: 0, roll: roll });
  g.restore();
  /* 逐像素找包围盒，收集 hs / ws */
}
ok('翻滚全程的实画高度不塌（最扁/最高 > 0.75）', hmin / hmax > 0.75, JSON.stringify({ hmin, hmax }));
```

**两个必须注意的地方：**

1. **画布要足够宽，否则宽度断言是在量空气。** 本项目第一次 `CW=300`、`SC=280`，
   角色手臂被画布裁掉，量出来 `wmin === wmax === 300`（正好等于画布宽）——
   比值恒为 1，断言形同虚设。留出角色最宽处的 1.2 倍以上。
   **凡是"比值恰好等于 1 / 恰好等于某个整数"的结果，先怀疑是饱和了。**
2. **写完必须反向验证一次**：把旧画法套回去跑同一个测量，确认它会 FAIL。

   ```js
   /* 旧画法：整只按 cos 压扁（下限 0.10） */
   const ca = Math.cos(roll);
   g.transform(1, 0, 0, ca, 0, -0.45 * (1 - ca) + 0.45 * (1 - Math.abs(ca)));
   E.paintEgg(g, plain, { /* roll 传 0，翻转由外层矩阵负责 */ });
   ```

   实测：旧画法 `ratio = 0.099`（最扁那帧只有 **27px** 高，肉眼就是一条线），
   新画法 `0.824`，阈值 0.75 —— 干净分开。**没有这一步，你不知道断言是真的在守门还是碰巧为真。**

### 4. 美术件多的时候，铺一张「总览图」逐件核对

整体截图里角色只有几十像素，看不出细节。**在 debug 钩子里把绘制函数和数据表一起暴露出去**：

```js
window.__EG__ = { paintEgg: paintEgg, data: { TOPS: TOPS, HATS: HATS, /* ... */ } };
```

然后在无头浏览器里往 DOM 塞一张临时 canvas，按分类把每一件单品都画一遍再截图：

```js
const lk = Object.assign({}, window.__EG__.look);
lk[cat] = item.id;
const u = Math.min(CS*0.78/0.80, CS*0.76/0.90);
c.translate(CS/2, CS*0.94); c.scale(u, u);
window.__EG__.paintEgg(c, lk, { t:0, blink:0, jump:false, arm:0 });
```

一次就能看出"袖子糊成一坨""衣服盖住裤子""腮红发灰"这类问题，比逐帧截图快十倍。

**坑**：`page.screenshot({clip})` 的裁剪区**必须落在 viewport 内**，超出部分会被截断/缩放，
看起来像"图片被裁了"。专门跑总览图的那次要把 viewport 放大（如 `760x900`）。

### 5. 姿态/精灵要裁切放大看

整体截图里角色只有几十像素，看不出问题。用 `clip` 裁切 + `deviceScaleFactor: 3` 放大：

```js
const clip = { x: 5, y: 380, width: 280, height: 320 };
await page.screenshot({ path: 'pose_run.png', clip });
```

配合清场（每帧清空障碍、锁血）单独截奔跑 / 跳跃 / 滑铲三个姿态。

**定格"动作中间帧"必须掐住 rAF，而且要掐两次。**

想在截图里抓到"翻到一半 / 扑到一半"的姿态，靠实时 rAF 是抓不到的（按键和截图之间它已经跑了好几帧）。
做法是停掉 rAF 再手动推固定帧数，但**下面这三步缺一步就会拍到错的画面**：

```js
await page.evaluate(() => {
  const E = window.__EL__;
  E.thaw();
  E.setUI('play');
  E.freeze();                 /* ① setUI 之后**立刻** freeeze */
});
await page.waitForTimeout(430);  /* ② 等 #menu 的 0.3s CSS 淡出走完 */
await page.evaluate(([fn, frames]) => {
  const E = window.__EL__;
  E.setLevel(1);              /* ③ 手动 tick 之前先复位到已知的干净落点 */
  E.RUN.state = 'play';
  E.setAdv(true);
  for (let i = 0; i < 8; i++) E.tick(1 / 60);   /* 前置帧数要小！ */
  E[fn]();
  for (let i = 0; i < frames; i++) E.tick(1 / 60);
  E.freeze();
}, [fn, frames]);
```

- **① 为什么必须在 `setUI` 之后立刻 freeze**：等 `#menu` 淡出的那 430ms 里 rAF 不会停。
  而 `setAdv(true)` 是**跨轮次残留**的状态 —— 第 2 轮开始等待时它还是 true，
  于是光在等待期间就自己跑了约 26 帧。**症状是"第一张没问题、后几张全错位"**，
  极难怀疑到"等 CSS 过渡"头上。
- **② freeze 停了 rAF 不会帮 CSS 过渡**，所以必须真的等。
- **③ 前置跑动帧数必须按"落脚台长度 / 速度"反算**。本项目起点预备台只有 4.2 长、
  `setLevel` 把人放在 `z=+1.6`、`WALK_SPD=5.1` ⇒ **约 30 帧就跑到台子边缘**。
  原来写「前置 34 帧 + 最多 22 帧」= 56 帧，拍到的"翻滚后半程"其实是**坠落途中**的蛋
  （整只在屏幕外，看着像美术 bug）。
- **每次截完打一行状态自检**，比事后看截图快十倍：
  ```js
  const st = await page.evaluate(() => {
    const e = window.__EL__.egg;
    return { mode: e.mode, y: +e.y.toFixed(2), roll: +e.roll.toFixed(2) };
  });
  console.log(name, JSON.stringify(st));     /* mode 必须是 run 才算踩实了 */
  ```
  帧数换算：翻滚 `ROLL_T=0.50s` ⇒ 60fps 共 30 帧，8 帧≈96°、15 帧=180°（最有说服力）、22 帧≈264°。


### 6. 「传送 + 状态」类断言的三个硬规矩

用 debug 钩子把人瞬移到某处再断言状态（测复活、测碰撞、测拾取）时，
下面三条几乎每个人都会踩一次，而且**失败现象会互相串味**，看起来像游戏有 bug：

1. **传送前必须等 `state === 'play'`。** 上一用例如果把人留在动画中途（如 `wetting` 溺水动画），
   下一用例一传送就被动画的状态机接管，症状是"几个看起来毫不相关的断言一起失败"。
   ```js
   async function awaitPlay(ms = 4000) {
     const t0 = Date.now();
     while (Date.now() - t0 < ms) {
       if (await p.evaluate(() => __EG__.run.state === 'play')) return true;
       await p.waitForTimeout(150);
     }
     return false;
   }
   ```
2. **别把 `skipTo(k)` 当成"安全落点"。** 这类钩子通常把人放在楼层/关卡的**中点**，
   而障碍也恰好摆在正中间（`t = T0 + i*(T1-T0)/(n-1)`，n=3 时中间那个就是 `t=0.5`），
   一落地就被弹飞，测"落水"根本没淹成。需要干净落点就自己算 `lerp(f.xa, f.xb, 0.09)`。
3. **往返方向的关卡（螺旋塔 / 折返跑）里，"往哪边走"取决于层号。**
   本项目偶数层 `dir=+1`、奇数层 `dir=-1`，障碍的 x 随 `t` 递减。
   写"走过去撞它"的测试若按 x 排序取第一个、再朝 +x 推，**在奇数层会把角色放在障碍下游、
   朝远离它的方向跑**，测出来撞击数恒为 0。正确做法是全部按 `dir` 归一化：
   ```js
   const c = E.run.obs.filter(o => o.f === k).sort((a, b) => a.x * dir - b.x * dir);
   E.P.x = ob.x - dir * ((ob.w + L.PW) * 0.5 + E.W * 0.06);   /* 从上游起跑 */
   E.IN[dir > 0 ? 'right' : 'left'] = 1;                      /* 朝推进方向撞过去 */
   ```
另外：**随机关卡布局会让"某一层刚好没有普通障碍"**（可能只生成了晾衣绳）。
测试要找"第一个符合条件的层"而不是写死层号，否则会间歇性失败。

## 角色绘制（骨架式，无需贴图）

- 用「两段肢体」画法：`legPath(hipY, ang, len, back)` 髋→膝→脚，`armPath()` 肩→肘→手。
- **返回关节末端坐标**，鞋/手用返回的坐标画；两处各算一遍必然对不上（会出现"鞋子漂在腿外面"）。
- ```js
  function shoe(foot, h, dir) {
    ctx.beginPath();
    ctx.ellipse(foot.x + h*0.030*dir, foot.y + h*0.004, h*0.068, h*0.042, 0, 0, TAU);
    ctx.fill();
  }
  ```
- **滑铲/低姿态一定要单独手绘，不要"整体旋转"**。整体 `rotate` 会把伸出去的腿转到地面以下，
  且躯干越低头越高。逐关节给坐标才可控；同时**跳过**外层的倾倒 `tilt` 旋转。
- 剪影要能在暗色背景上看清：深色底 + 亮色主色（如青绿连帽衫）+ 暖色轮廓光
  （`globalCompositeOperation='lighter'` 描边，注意叠在亮色上会发白，alpha 压到 0.6 左右）。
- 围巾/斗篷用一条带正弦扰动的二次贝塞尔曲线，成本低但动感提升很大。
- `const` 声明若在 `ctx.save()/translate` 之后用到，会触发 TDZ `Cannot access 'x' before initialization`——
  姿态分支用到的变量（如 `sliding`）必须在变换之前声明。

## 可调视角（抬头 / 低头看路）

需求常是「可以调节屏幕方向，往上看」。做法**只改投影函数**：

```js
var camPeek = 0, camPeekT = 0;                       /* 当前值 / 目标值 */
function sY(z)    { return H * 0.62 + camZ + camPeek - z; }
function sYinv(sy) { return camZ + camPeek + H * 0.62 - sy; }
/* 上限：别让角色掉进左下/右下那两块虚拟按键区 */
function peekMin() { return -H * 0.18; }   /* 低头：看得见追上来的水 */
function peekMax() { return  H * 0.20; }   /* 抬头：看得见上面的路 */
```

- **物理一行都不碰**。碰撞、落点、判定全用世界坐标 `z`，所以玩法在数学上零变化，
  机器人回归必然与改前完全一致 —— 这是"零风险加功能"的正确姿势。
  如果去动角色的世界坐标或重力，就得重跑整套数值验收。
- 每帧只做 `camPeek += (camPeekT - camPeek) * min(1, 13*dt)` 跟手插值，再 `clamp`。
- 输入给三种，手机和桌面都能用：**竖向滑条**（指针按下时按位置直接跳，再跟手拖）、
  **直接拖画面**（`touch-action:none` 的 canvas 上监听 pointerdown/move/up）、键盘 `q`/`e`。
  给 canvas 拖拽加 `setPointerCapture` —— 否则手指划过角落按键时事件会被那些 DOM 抢走。
- **松手后停在原处，不要自动回中**：用户说"调节"就是想设置住；只有说"偷瞄/看一眼"才做回弹。
  重开一局时归零。
- 上限的算法：角色脚点屏幕高度 = `0.62H + camPeek`。抬到 `+0.20H` → 脚在 `0.82H`。
  看着危险，但**角色是横向居中的，而两组按键在四个角落**，所以实际上不会真被挡住 ——
  算之前先想清楚横向位置，别白白把视角范围砍掉一半。

## 程序化配色 / 「无限生成不同场景」的做法

用户原话常常是「**跑到一定程度就继续生成不同场景**，不用我再手动加了」。
正确解法不是做几百套主题，而是**以已有的几套为底料，在现场转色相生成**：

```js
/* 11 个色环转角 × 5 套底料 = 55 种组合；名字由确定性随机拼出来 */
var HUE_STEPS = [150, 42, 288, 196, 88, 318, 236, 24, 120, 260, 68];
function levelAt(n) {                       /* n 不封顶 —— 这就是"无限" */
  var si = SCENE0 + (n - 1);
  if (si < LEVEL_N) return LEVELS[si];
  var k = si - LEVEL_N;
  if (!sceneCache[k]) sceneCache[k] = genScene(k);
  return sceneCache[k];
}
```

### 四条铁律

1. **只转色相 ≠ 变风格。** 这是最容易翻车的一条。糖果淡彩绕色环转 150° 还是糖果淡彩，
   只是换了色。实测爬到第 14 层看到的仍是一屏洗淡的粉橙。
   必须 `rotHue` **再** `punch(satK, lightK)` 两步走，顺序不能反：
   ```js
   var t = mapThemeDeep(rotThemeDeep(base, HUE_STEPS[k % 11]),
                        function (c) { return punch(c, 1.35, -0.085); });
   ```
   基础套只需要 `punch(c, 1.22, -0.070)`；生成套要更狠。
2. **白色是饱和度为 0 的颜色，`punch` / `rotHue` 对它完全无效。**
   本项目台面 `top` 好几套本来就是 `#ffffff` → 生成的浓色场景里留下一整块洗白的板子，
   屏幕下半部全毁在它身上，而它自己"看起来很正常"。
   判据 `rgb2hsl(parseCss(c).rgb)[2] > 0.90` 就用 `setLight(base, l)` 染上本关色相。
   ⚠ **顺序：先压深基色、再取浅色**，反过来的话顶面会相对偏亮，还是洗白。
   分道线同理（白色 `lane` 在浅台面上等于没画）。
3. **必须确定性。** 掉下去复活会重跑 `buildLevel`，用 `Math.random()` 的话颜色当场换一套，
   玩家会以为"复活到了别的关"。用 `hash01(k) = fract(sin(k*127.1+311.7)*43758.5453)` + 缓存。
4. **`id` 必须换掉**（`t.id = 'gen' + k`）。沿用底料 id 会误命中 `#stage[data-theme="xxx"]`
   这类 CSS 选择器，症状是"某个生成的场景长得跟别人不一样"。

### 颜色工具链要"类型守恒"
主题里 `fog` / `railTop` / `abyssTop` 会被 `hexA()` 吃（它**只认 `#rrggbb`**，
`replace('#','')` 拿不到 `#` 就 `parseInt` 出 NaN）。所以：
**hex 进 hex 出** —— `rotHue`/`punch`/`setLight`/`mixCss` 都必须按输入的格式输出
（`parseCss` 记一个 `hex: true`，`emitCss` 按它决定输出 `#rrggbb` 还是 `rgb()`/`rgba()`）。

## 长距离渐变 + 雾：接缝为什么总在地平线

这是"上下两块大色域拼在一起"的通用坑，跑酷/追尾视角里必然遇到。

- **天空的雾带只画到地平线，而地平线以下被深渊（水面/云海）整块盖掉 —— 接缝就是这么来的。**
  上面被雾提亮、下面又浓又深，中间一条**硬边**，整屏看着像两张图拼起来。
  修法：画深渊时把**同一层雾越过地平线再往下铺一段**
  （`HORIZON - 0.05H → HORIZON + 0.105H`，浓度从顶到底归零）。
  两边必须用**同一个浓度函数**，各自调浓淡接缝会重新露出来。
  这顺带也就是"远处的深渊被雾罩住"的大气透视，本来就该有。
- **深渊和天空是同一套色相转出来的 → 上下同色、没有纵深。**
  只压明度不够（上面亮红、下面暗红 = 整屏一个色调）。要**往近黑的冷色里混一档**
  把色相压掉大半，只留一点本关暗示，上面的霓虹才跳得出来：
  ```js
  t.abyss = [mixCss(shade(t.abyss[0], -0.30), '#0b0d18', 0.60),
             mixCss(shade(t.abyss[1], -0.46), '#05060d', 0.70)];
  ```
- **怎么量（做成回归断言）**：`freeze()` 之后 `getImageData`，
  逐列比较"地平线上方 7px / 下方 7px"的色差，取**中位数**。
  ⚠ 必须用中位数 —— 单点极值会被中间的塔柱/主体带偏；
  也别写成"整行的连续区间均值"，那会把塔柱算进去，读数完全是错的（本项目第一版就写错了）。
  实测：改前中位 **86.7/255** → 改后 **28.2/255**，阈值取 60 守住。

## `x = f(x); x = g(x);` 连着两行不是"覆盖"，是**复合**

本项目真实踩到，而且**看起来像死代码**：
```js
t.abyss = [shade(t.abyss[0], -0.26), shade(t.abyss[1], -0.40)];
t.abyss = [shade(t.abyss[0], -0.20), shade(t.abyss[1], -0.30)];   /* 读到的已被压过一次 */
```
第二行读到的 `t.abyss[0]` 已经是第一行的结果 → 实际是 -0.408 / -0.58，深渊被压成纯黑、色相尽失。
我把它当死代码删掉之后，深渊当场从近黑变成亮绿/亮橙，整屏反而发闷没有纵深。
**教训：删任何"重复赋值"之前，先看清第二行有没有自引用。**
凡是要叠加两级，就写成一行显式的合并值并写清注释。

## 性能：量「单帧绘制耗时」比量 rAF 帧率可靠

- **headless Chromium 的 rAF 帧率被合成 / 刷新率主导**，做 A/B 会得出**相反**的结论。
  本项目真实例子：把新加的绘制（塔身 + 环 + 浮尘）全部关掉，反而量到 0.58ms，
  **比全开的 0.44ms 还高** —— 那个 A/B 的结论完全是噪声。
- 直接量 `freeze()` 连画 120 次的均值才是真数。本项目 0.41~0.49ms/帧，
  60fps 的预算是 16.7ms → **JS 侧可忽略**，帧率差距来自新增的**绘制像素量**与合成。
- 昂贵的是**大描边**：一笔 40px 宽、周长上千像素的 `shadowBlur`/粗描边能吃约 5ms。
  想要辉光就用**两层描边**（粗而淡做底 + 细而亮做芯），不要 `shadowBlur` 外发光。
- 粒子数也要克制：本项目浮尘 30 → 22 颗。
  粒子的位置**由 `z` 决定 + 按固定 `span` 周期循环**，不要每帧 `Math.random()`
  （那会变成乱抖的噪点，而不是漂浮的尘埃）。

## 「无限复活 / 取消生命系统」类的需求

常见的用户原话是「可以无限复活，掉下去就是重新来，不要生命限制」。
这不是"把 hp 删掉"那么简单，有三条必须一起想清楚：

### 1. 先确认"在这个关卡几何里，到底能不能真的掉下去"
**不要假设"掉落"存在。** 例如螺旋上升塔：每层在 x 方向铺满（`x0=-XR, x1=+XR`），
x 还被 `lim = XR - 0.18*PW` 夹住 → **根本不存在踩空坠落**，唯一的落水方式就是水涨上来。
于是"复活回到本关起点"在几何上直接不成立：每层是「平坦台子 + 末段上坡」，
水平段高度恰好等于该层基准高度 `k*FH`，**水淹到你时这一关的起点必然已经在水面下**，
把人放回起点 = 一复活就再淹 = 无限死循环。

> 结论：先花五分钟把这个几何算清楚再动手。算清了只需要补一条规则；
> 写完了才发现，就得返工整套重生逻辑。

### 2. 复活点 = "本关起点" + **把水位压回去**；退回量必须又小又够用
```js
/* 只压到"这一关起点刚好露出脚面"，多一点都不给 */
RUN.waterZ = Math.max(WATER_BASE,
  Math.min(RUN.waterZ, k * L.FH - L.PH * 0.25 - RUN.waterRate * L.DRY));   /* L.DRY = 2.6 秒 */
```
- `L.PH * 0.25` 是"露出脚面"的余量；`waterRate * L.DRY` 是**给玩家的反应秒数**。
  **两者缺一不可**：只有余量的话，水在 0.2s 内就追回来，玩家一醒来又淹，体感是卡循环。
- **绝对不要退一整层** —— 那样"反复溺水"会变成"把水刷下去"的白嫖手段。
- **更不要在被淹时把玩家往上顺延一层**。这条很容易想当然地当成"更宽容"，
  实际是致命 bug：水一直把你顶到上一层，**躺着不动就会被水被动推上塔顶而通关**
  （每层被推上去的速度 ≈ 水涨的速度）。我推演过这个数字才排掉它。

### 3. 取消生命之后，"唯一的失败条件"必须显式补上，配套道具要一起改
```js
RUN.left = Math.max(0, RUN.left - dt);
if (RUN.state === 'play' && RUN.left <= 0) { RUN.state = 'dying'; RUN.endT = 0; }
```
- 很多游戏原来根本没有"超时判负"的代码 —— 因为原来的失败是"血扣光"，
  而"时间到"是靠**水位恰好涨到顶**这种隐式方式兑现的。血一删，压力体系就整个塌掉。
- **所有"补心/回血"类道具会立刻变成空壳**，必须一起改语义（否则提示语在骗玩家）。
  本项目补给箱改成"退水位 + 补时"，两者天然同步，因为 `waterRate` 就是"每秒涨多少水"：
  ```js
  function pushWaterBack(dz) {                 /* 退水 = 补时，两个显示永远对得上 */
    var room = Math.max(0, RUN.d.sec - RUN.left);
    dz = Math.min(dz, room * RUN.waterRate, RUN.waterZ - WATER_BASE);   /* ← 关键：先用时间余量夹住 dz */
    if (dz <= 0) return 0;
    RUN.waterZ -= dz;
    RUN.left += dz / RUN.waterRate;
    return dz / RUN.waterRate;
  }
  ```
  `room * waterRate` 这一步不能漏：否则时间会被上限截断、而水位照退，**两个显示就脱钩了**
  （实测：水位退了 87px、本该补 25s，但倒计时只剩 18.6s 可补）。
- 生命系统要删干净：`DIFFS[].hp` / `RUN.hp` / `RUN.maxhp` / HUD 元素 / CSS 规则。
  写个 grep 扫一遍 `\.hp|maxhp|hHeart` 确认没有残留引用（少删一处就是运行时 TypeError）。

### 4. 顺带收益：HUD 常常因此才放得下
"去掉生命显示"很常顺手解决 HUD 挤爆的问题（见「常见坑」里 flex 塌陷那条）。
本例删掉 6 颗爱心后卡片自然回到自然宽度。**但别忘了回头量一遍所有元素的总宽。**

## 常见坑

- **flex 行里内容最"软"的那一项会被压到 min-content；中文可断行 → 直接塌成 1 个字宽的一排竖排字。**
  只要子项自然宽度之和 > 容器宽度就必然发生，而且**不溢出、不报错，只是悄悄变丑**，
  截图里表现为"某个卡片里每个字占一行"。
  诊断：临时给各项设 `flex:none` 量出自然宽度求和，与容器宽度对比即可定位。
  ```js
  document.querySelector('.hcard').style.flex='none';
  document.querySelector('.hheart').style.flex='none';
  /* 量完记得改回来，或者只在 probe 里量 */
  ```
  修法只有两条路：**改两行**（每行 2~3 项），或者**缩文案 + 统一缩小字号**。
  三条各 ~130px 的项目在一行 339px 里是塞不下的，别指望微调间距能救。
  **量的时候一定要按"最宽的那一档数据"量**（本项目地狱档 36 关 vs 初级 24 关，
  文案宽度都不一样），只量当前这一局会漏。
  本项目这个塌陷最后是**因为改玩法（删掉生命显示）顺手解决的** ——
  所以遇到"改玩法"的需求，回头看一眼旧缺陷有没有被顺手消掉，别白留。
- **覆盖层 `pointer-events:none` 会连子按钮一起屏蔽**：canvas + DOM 混合的游戏里，
  UI 覆盖层通常写 `.ov{pointer-events:none}` 好让 canvas 收事件，但**子元素不会自动恢复**，
  必须给按钮显式 `pointer-events:auto`。现象是"按钮看着完全正常、点下去毫无反应"，
  截图永远发现不了 —— 一定要用无头浏览器**真点一次**关键按钮。
- **Web Audio 的 `AudioParam` 不能直接赋值**：`bp.Q = 1.2` 抛
  `Cannot set property Q which has only a getter`，必须 `bp.Q.value = 1.2`；
  而 `frequency.setValueAtTime()` 又是正常写法，两种混用极易漏。
- **切换场景要重置上一场景的状态变量**：`pickT`、`elapsed` 这类隐含状态如果不在切场景时归零，
  会让新场景里的判断永久短路（本项目"换一只蛋仔"按钮就因为 `pickT` 停在 1.05 而完全失效，
  而它看起来、摸起来都像个正常按钮）。
- **子元素要在 DOM 里才能读布局尺寸**：给缩略图 canvas 设像素尺寸前必须先 append，
  否则 `clientWidth` 是 0，要留兜底默认值。**而且 append 之后要等到下一帧才画得出内容** ——
  无头测试里点完分类要等 ~400ms 再截图，否则抓到的是空白缩略图。
- **无头测试里出现"恒为 0 / NaN"的断言，先怀疑断言自己在量空气，而不是产品坏了。**
  本项目真实例子：为了量"轮廓最宽处"写了
  `g.isPointInPath(px, py)`，坐标用的是 `y = -0.95*400`（设备像素），
  而轮廓路径是**单位坐标画在原点**、画布又没做任何缩放 →
  那个点永远在路径外，`widest` 恒为 0，`ratio` 变成 `NaN`，**断言一直是坏的却没人发现**。
  正确做法：直接把几何函数（半宽表、外扩曲线）暴露到 `?debug=1` 的调试钩子里去量，
  又快又不会被手臂/脚/粒子污染。
  ```js
  window.__EG__ = { /* ... */ eggHW: eggHW, skirtW: skirtW };
  ```
  **凡是"看数值就能判定"的美术/几何回归，都应该写成这种函数级断言**，
  而不是截图人眼比对 —— 下一轮改动才拦得住。
- **渲染循环里每帧重建 DOM**：`innerHTML` 只在字符串变化时才写（缓存上一次的值）。
- **`ctx.save/restore` 必须严格配对**，尤其是加了姿态分支之后；分支里漏掉 restore 会让后续所有绘制错位。
- **前景区（贴着镜头快速掠过的碎屑）** 不要放在屏幕最下沿，会被裁切得像"脏点"；
  放在地面带的中段，并给个暖色顶面高光。
- **结算/统计数字要 `Math.floor`**，否则长小数会撑破布局，视觉上糊成一团。
- **音效必须在用户首次交互后**初始化 AudioContext（`pointerdown`/`keydown` 一次性监听），否则被浏览器策略挂起。
  环境音用低增益噪声 + 缓慢 LFO 扫低通，成本极低但氛围提升明显。
- **一排图标型 HUD（爱心/星星）数量别超过设计时的那几个**。爱心从 5 个加到 6 个就会顶出屏幕右边，
  而它在截图里只表现为"最后一个被切了一半"，很容易忽略。加血量上限时要么缩小图标，要么改成
  「一个图标 + 数字」。
- **卡片式列表用 `grid` 而不是 `flex`**：左侧图标 + 右侧标题/时间 + 下面一行描述这种结构，
  用 `flex` 会把描述挤成 3~4 个字一行的窄条（"水位爬／得很／慢"）。
  正确做法是 `grid-template-columns: auto 1fr auto` + 两行，把描述放到第二行跨列；
  包着标题和描述的中间层用 `display:contents` 让它俩直接参与网格，HTML 不用改。
- **胜利/通关判定一定要反解"最远能走到哪"**。凡是"爬到某个高度/走到某个位置算赢"的玩法，
  都要确认那个判定点距角色可达边界还留着几十像素余量，
  否则玩家得贴着边界蹭才能触发，表现为"明明到顶了却不算赢"。
- **别用整体降透明度来表示"角色在遮挡物后面"**。`ctx.globalAlpha = 0.42` 会把蛋仔连同五官一起
  洗淡，跑酷里角色看不清＝直接劝退，而且"淡"并不等于"在后层"，玩家读不出来。
  正确做法是**角色永远实心画在最上层**，用一个独立的前景标记（暖色描边 / 柔光）讲"人在柱子后面"。
- **低透明度亮色叠在深色背景上会合成成脏色**，这一点必须实测算数而不是凭感觉：
  金色 `#ffd451` 取 `globalAlpha=0.30` 叠在深蓝灰 `rgb(40,45,60)` 上，
  实际输出是 `rgb(156,129,99)`——一团浑浊的土褐色，看起来像渲染 bug 而不是高亮。
  想让高亮"亮"就必须**两层叠**（外层宽而淡 + 内层窄而亮），或者干脆用
  `createRadialGradient` 做柔光晕。凡是硬描边、光环、光标这类元素，都要在**最暗的那张背景图上**确认对比度。
- **在无头浏览器里读 canvas 像素做断言时，有三个必踩的坑**：
  1. **改完状态必须等真正的下一帧画完再读**，否则 `getImageData` 拿到的是**上一次**的 canvas。
     现象极具迷惑性：A 组标"应该有"却测得 0、B 组标"应该没有"却测到一堆，两组结果正好互换。
     必须在 `page.evaluate` 里 `await new Promise(r => requestAnimationFrame(() => requestAnimationFrame(r)))`。
  2. **canvas 的 backing store 尺寸 ≠ viewport × `deviceScaleFactor`**。游戏为了性能普遍把
     DPR 截断在 2（`dpr = Math.min(devicePixelRatio, 2)`），所以 `deviceScaleFactor: 3` 时
     `canvas.width` 仍是 `rect.width * 2`。算屏幕坐标一律用 `cv.width / cv.getBoundingClientRect().width`
     现场求，不要拿 `deviceScaleFactor` 当 DPR。
  3. **改美术会悄悄污染按颜色做的像素断言**。本项目给台面换成木板后，
     暖棕色木板本身命中"金色"判据（`r>150 && r-b>55`），基线从 73 涨到 287。
     断言还成立（2727 vs 155 = 17.6 倍）纯属侥幸。
     **正确做法是把采样区限制在不会被新美术碰到的地方** —— 例如只数"角色脚底往上"那一段，
     避开通铺的台面；并把判据从"绝对像素数"换成"两组之间的倍数"。
     凡是重构了配色，都要回头看一眼颜色类断言有没有失去区分度。
  第 1、2 条合起来的典型症状是**"断言窗口和实际命中像素对不上号"**（算出的扫描区间根本框不住命中的像素 x 坐标）——
  一旦发现"窗口对不上"，先怀疑它们，而不是怀疑游戏逻辑。
- **间歇性 FAIL 的第一反应：先问"这条断言量的是产品契约，还是无头环境的时序"。**
  真实例子：`松开「前进」立刻停住` 量"松手后一帧内的位移 ≤ N 帧 × WALK_SPD"，
  5 轮挂 2 轮。查下来**不是产品问题** —— 第二段区间在所有轮次都恒为 `0.0000`（真的停住了），
  第一段那点位移是 `mouse.up()` 走 CDP 往返的**输入延迟**（实测约 50ms ≈ 3 帧，场景越重越久）。
  这个阈值被放宽过一次（1.6 帧 → 2.5 帧）还是超，说明**方向就是错的**。
  改成量真正的契约：
  ```js
  gz2r.adv === false                    /* ① 松手后按钮真的放开了 */
  && Math.abs(gz3 - gz2) < 0.02         /* ② 紧接着的 400ms 位移恒为 0 */
  && Math.abs(gz2 - gm.z) <= 6*5.1/60   /* 第一段只当兜底，不卡精确帧数 */
  ```
  之后连跑 5 轮全绿（第一段在 0.08~0.17 之间）。
  **凡是"等一下再读"的断言，都不要把等待时长当判据。**
- **像素 / 颜色类回归的阈值用「多档的均值」，不要用"最差那一档"。**
  另一边会抖的量（本项目是**云的初始位置来自 `Math.random`**，每次加载不同）
  会让最差档在 46~61 之间跳，单档阈值必然间歇失败。
  换成"九套场景各自的**中位数**再取**均值**"就稳在 26.8~31.3（改前 86.7），
  阈值 45 两边余量都很大。**先跑 4~5 轮看数据分布，再定阈值和统计量。**
- **回归断言里的"中位数"要选对样本**：本项目量地平线接缝时，
  一开始写的是"整行连续区间的均值"，把**中间的主体（塔柱）**算了进去，读数完全是错的。
  正确做法是**逐列**求色差再取中位数 —— 极端值（主体边缘）会被中位数自然剔除。

## 交付前自检清单

1. `node --check` 过一遍抽取出来的脚本（`<script>` 内容单独存文件再 check）。
2. 无头浏览器跑：`pageerror` / `console.error` 必须为空。
3. **真实点击一遍所有按钮和可点区域**（不是只调 debug 钩子）：断言状态真的变了。
   截图看不出"按钮点不动""场景切不回去"这类问题。
   **布局断言（量 `getBoundingClientRect` 算不重叠、在屏内）只证明"长在对的地方"，
   完全不证明"按得下去"。** 覆盖层的 `pointer-events:none`、按钮上的 `transform` 呼吸动画、
   事件绑错元素……都会让一个看着完全正常的按钮毫无反应。所以每个键都要用**真指针事件**按一遍。
   **要按"按键的绑定方式"分两种按法**（`bindTap` 认 `click`，`bindHold` 认 `mousedown`）：
   ```js
   const KBOX = async (id) => await S(`(() => {
     const r = document.getElementById(${JSON.stringify(id)}).getBoundingClientRect();
     return { x: r.left + r.width / 2, y: r.top + r.height / 2 };
   })()`);
   const press = async (id, holdMs) => {          /* 长按型：down → 保持 → up */
     const c = await KBOX(id);
     await page.mouse.move(c.x, c.y);
     await page.mouse.down(); await page.waitForTimeout(holdMs); await page.mouse.up();
   };
   ```
   每个键按完断言**它该产生的那个状态**（`egg.mode === 'air'` / `rollT > 0.3` /
   `diveT > 0.2 且碰撞盒压到 0.52` / `x` 换道方向），而不是只看 `classList` 有没有 `.dn`。
   **⚠ 松手类断言要给"一帧"的余量**：`mouse.up()` 派发到游戏处理之间，rAF 可能已经带着
   按住状态起了下一帧（实测残余恰好 `WALK_SPD/60 ≈ 0.085`）。
   正确写法是量**松手之后的第二段区间**必须恒为 0，而不是纠结第一段那 0.085。
   **滑条 / 拖拽这类连续控件要用真指针事件拖一遍**（`mouse.down` → 分段 `mouse.move` → `mouse.up`），
   并断言"按下→拖动→松手"三个阶段各自的读数；只调 setter 是测不出事件绑定漏了的。
   注意两次拖拽之间把指针**移到别处再按下**，否则首尾坐标重叠会让后一次拖拽出现假结果。
4. 机器人满难度长跑 45s，确认难度落在"10~20s 掉 1 血"区间（动作类）。
   **改玩法的回合要重新定义"跑赢了"的标准**：本项目取消生命之后，
   机器人的判据从"0 掉血"改成"0 被撞 / 0 复活全通关"，
   并且 `while` 循环的跳出条件要从 `state !== 'play'` 改成 `state === 'over'` ——
   否则一旦出现复活/溺水这类中间态，机器人会**提前收工**，看起来像"跑完了"。
5. 裁切放大看角色姿态 / 美术件总览图 / 菜单页 / 结算页（或换装页）。
   —— 重点确认角色在**最暗的场景**里也够亮、够清晰；任何"高亮/光环"元素都要在暗背景上复看一次。
   美术配色一改，**按颜色做的像素断言要回头重看有没有失去区分度**（暖棕木板会命中"金色"判据）。
6. 桌面横屏确认手机画框居中、宽高比正确。
7. **改了规则就要改文案**：难度页说明、开局提示、结算页失败原因、
   以及所有会在新规则下变成"空壳"的道具提示语，都要一起过一遍。
   本项目因为"无限复活"，失败原因从"体力耗尽"改成"时间到 · 水到第 N 关，你还在第 M 关"，
   补给箱从"+1 心"改成"水位退了一截"。
8. 玩法类改动收尾时扫一遍**残留引用**（grep `\.hp|maxhp|hHeart` 之类），
   少删一处就是隐藏的 `TypeError`。
9. 用 `present_files` 打开预览交付。

## 发布（sites）之后：怎么确认**线上真的是新版**

`verified: true` 只说明"域名能打开"，**不说明打开的是你刚传的那一版**。
发布只覆盖同名 app，链接不变 —— 于是"我明明改了，线上还是旧的"极易被当成缓存问题放过去。
三层验证，缺一不可：

1. **字节级**：`curl` 抓线上 HTML，比**行数 + 字节数 + 新版独有特征串**。
   ```bash
   curl -s "https://<域名>/?_=$(date +%s)" > /tmp/live.html
   wc -lc /tmp/live.html
   grep -o 'id="kDive"\|rollFlip\|tutuPath' /tmp/live.html | sort | uniq -c
   ```
   特征串要挑**这一版才有的标识符**（新加的按键 id、新函数名）；挑文案会被 HTML 转义坑。
2. **加载级**：无头浏览器打开**线上 URL**，收 `pageerror` / `console error`，断言为 0；
   再量一遍按键 `getBoundingClientRect()`，与本地对照（布局在真机上会不会被挤掉只有这一步能发现）。
3. **操作级**：在线上页面**真按真点**，并断言可观察的状态变化。
   本项目：点 `#btnPlay` 出发 → 按住 `#kGo` 1.6s（HUD 里程 2m→6m，证明真的在走）→
   点 `#kDive` → 截图里蛋仔压平前倾贴地飞。

两个坑：
- **线上 URL 不带 `?debug=1` 时调试钩子不存在**（`window.__EL__` 取不到），这是**设计如此，不是坏了**。
  线上探针只能靠 DOM + 截图，不能调钩子。别为此把钩子常驻暴露出去。
- **脚本放在 `/tmp` 跑会解析到另一个版本**的 playwright（报缺 `chrome-headless-shell-1217`）。
  必须显式 `chromium.launch({ executablePath: '…/chromium_headless_shell-1243/…' })`，
  和项目里 `dev/.shot.js` 用同一个可执行文件。
