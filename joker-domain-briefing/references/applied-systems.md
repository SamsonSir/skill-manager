# 从系统资料到具体操作

用于用户读过访谈、案例或专业文档，但不清楚如何把机制落到已有工作场景。先定位材料中对应段落，区分来源主张、已核查事实和为解释而提出的示例。

## 解释路径

先用业务语言解释机制，再说明它由什么文档、配置或程序实现。例如 system foundations 可能指数据语义、工具接口、身份权限、执行状态和恢复能力，不自动等同于 system prompt，也不默认要求重建数据库。

按用户的问题选择步骤，每个关键步骤说清“谁拿到什么 → 做什么 → 留下什么 → 如何验证”。沿用用户提供的业务；尚无具体流程时用一个明确标注的示例串起解释，不把示例写成已确认需求。

- 改造现有系统：走查真实正常和异常流程 → 盘点已有系统、数据和可访问接口 → 找出缺失能力 → 补数据口径、映射与工具约定 → 补权限和状态恢复 → 对照试运行、受控切换。优先复用现有能力，是否迁移或重建需要具体证据。
- 新建系统：明确业务闭环及完成标准 → 定义数据、角色、状态转换和接口 → 实现一条含失败路径的完整流程 → 接入 Agent → 按实际风险验收和逐步上线。

两类场景都应指出哪些由用户组织确认、哪些由业务负责人决定、哪些由开发或原厂商实现。架构名词只有连接到实际产物时才有帮助。

## 防止纸面落地

- 工具说明应能解释输入、输出、前置条件、业务副作用和失败结果。重复请求、超时后的未知结果与明确业务拒绝分别处理。
- Prompt 中的身份与权限说明不替代服务端校验；聊天记录不自动成为经过审核且有访问边界的业务资产。
- 开发流程或 AEG 的验收门禁与业务系统运行能力分开核对；文档齐全不代表功能已实现。
- 具体接口、现有系统能力和材料未给出的运行数据保持待验证，不以案例描述当作目标系统事实。

只输出当前困惑所需的步骤和证据，不附带完整项目方案、统一技术栈、工具采购清单或固定周期。
