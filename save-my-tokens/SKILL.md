# save-my-tokens

给用户的 Claude Code / Codex 配置做体检。脚本读本机日志，量出每个新会话开局就带上的 token 由哪几块组成，以及装着的 skill、MCP、规则近 30 天用了几次；你拿这些证据和用户逐项定去留，他同意的才改，改前备份，可以回滚。

脚本在本文件旁边：`python3 <本目录>/scripts/slim.py`，下面简写成 `slim`。只用 Python 标准库，参数用 `slim <子命令> -h` 查。用户的电脑是 Windows 时，先读 `references/windows.md`。

## 怎么跟用户说话

- **先讲是什么、动了会怎样，再讲键名**。用户不一定熟悉这些配置，商量时用平常话；`skillOverrides` 这类键名放进最后的改动清单。用户自己用键名说话时，你也直接用。
- **先说大的**。按报告开局部分的大小顺序走，最大的、能动的那一块先谈。
- **每一轮结尾报位置**：「到现在还没改任何东西，改动清单里有 N 项，还剩哪几块没看」。
- **敏感内容只报名字和大小**：密钥、token、环境变量的值、规则文件里的私人内容，回复里不出现原文。

## 1. 扫描

```
slim scan --json <系统临时目录>/save-my-tokens-scan.json
```

只读，不改任何文件。在哪个目录跑都一样：它读的是用户级配置，加上近 30 天开过会话的所有目录。日志多时要跑一两分钟，先跟用户说一声。输出是一份中文报告；`--json` 那份留着，后面取名单、核对都用它。

报告开头的「注意」行（日志只覆盖了几天、没有日志、配置解析失败）决定后面的「0 次」能不能信，原样转告用户。

## 2. 先讲开局账单，定顺序

报告的第一部分「开局」是 Claude Code 自己记在日志里的实测：新开一个会话，第一次请求带了多少 token，这一次请求里每一块多大。用五六行讲给用户：

1. 新开一个会话的第一次请求带了多少 token（中位数），最常用的那个目录是多少。
2. 这一摞从大到小是什么，哪几块是固定的，哪几块能动。
3. 你建议的顺序：从最大的能动的那块开始。规则文件比 skill 清单大的时候，先谈规则文件。
4. 流程：一块一块选，选的时候什么都不改；全部选完，他看过整份清单，再一次改完；改之前备份，随时能退回。

然后问他照这个顺序走，还是想先看哪一块。整份报告留在你这里，按块取用。

报告写「这一块量不出来」时：请用户新开一个会话，什么都不说，输入 `/context`，把结果贴过来，用它代替。

## 3. 清理：每次请求都带着、可以拿掉的东西

每一项都按同一个顺序：摆证据 → 给选项和你的倾向 → 用户拍板 → 记进改动清单。**这一步只记不改**，备份和修改都留到第 5 步；用户中途想看效果，告诉他现在还没改、改完要新开会话才看得到。同类的成组问；带 ⚠ 的逐个讲。

「0 次调用」是**候选**，不是结论：它只说明这个时间窗里的日志没看到。

### 规则文件

报告里规则文件那一节按大小列了每个文件，大的还列了最大的几节。规则文件在会话一开始整份加载，之后每句话都带着，所以它常常比 skill 清单大得多。先看开局部分列出的那几个文件，它们才是这次开局带上的；标着「Codex 读的」只算在 Codex 的会话里，用户不怎么用 Codex 时放到后面。对每个大文件，读它，再按节和用户商量，每节四个去向：

| 去向 | 做法 | 适合 |
|---|---|---|
| 留着 | 不动 | 每次对话都用得上的规矩 |
| 用到再读 | 把这一节搬进单独的文件，放在原规则文件的同一个目录里，原处留一行「做某事之前先读某路径」 | 只有做某类事才用的流程、长清单、索引 |
| 碰到某类文件才加载 | 搬进那个项目的 `.claude/rules/<名字>.md`，开头写 `paths:` 和匹配的文件范围 | 只跟某些目录或文件类型有关的规矩 |
| 做成 skill | 一整套步骤搬成一个 skill | 可以点名调用的完整流程 |

- 「用到再读」留下的那一行写成普通的一句话加路径。写成 `@路径` 会让那个文件照样在开局加载，等于没搬。
- 这一行决定模型到时候去不去读：写清楚**什么情况下**要读。用户担心「该用的时候没读到」，就把触发条件写具体，并告诉他改完先用几天，不顺手随时退回。
- 只做搬动、删除、合并；保留里面的具体事实（命令、路径、数字、项目结构）；每一处改动都让用户看过 diff。
- 「超过官方建议的 200 行」只是一个事实，删哪些内容不凭长度判断。

**自动记忆**：报告列了 Claude Code 自己记的 `MEMORY.md`。它的开头 200 行或 25KB 每个会话都加载；标了「超过」的，后面的部分开局读不到。它不在开局部分「规则文件」那一行里，讲账单时单独提。两个选项：用户有自己的知识库或记忆办法，关掉它（见第 4 步的开关）；想留着，请用户自己打开那份文件删掉过时的条目，这份文件你只读。

**Codex**：报告写某个项目的 AGENTS.md 超过 `project_doc_max_bytes` 时，Codex 只读得到开头那一段。两条路让用户选：把文件瘦下来，或者把这个上限调高（每个 Codex 会话都多带这么多）。

**重复**：报告把重复分成两种，处理方式不同。

- **同一会话重复加载**（比如全局 CLAUDE.md 和项目 CLAUDE.md 里同一条）：每次请求都多带一遍。问用户留哪一处。标 `≈` 的是两处措辞有出入，先问哪份是新的。
- **两个 agent 各一份**（CLAUDE.md 对 AGENTS.md）：Claude Code 和 Codex 各读各的，这不是重复付费。只处理有出入的那几条：问哪份是对的，把另一份同步过去。同一个项目里两份几乎一样时，可以提议让 CLAUDE.md 只写一行 `@AGENTS.md` 再加 Claude 专属的几条。

两个文件算不算「同一会话一起加载」，以报告的标签为准；每个项目实际加载哪些文件，在 json 的 `projects[].claude_files` 和 `codex_files` 里。脚本只找得到逐条相同和措辞相近的；意思相同、写法不同的重复，你读文件自己找，找到后先对照加载清单确认两个文件确实一起加载，再提出来。报告写「有 N 组项目目录的规则文件内容完全相同」时，同组的其他目录（多半是 worktree）在 json 的 `projects[].same_as` 里，改之前告诉用户它们不会跟着变。报告列出的「写了 `@路径` 但文件不存在」是候选：先打开那一行确认它确实是引用，再问用户改路径还是删掉。

**规则写得好不好**（旧模型时代的写法、指向不存在的文件或命令、互相矛盾的规则）交给 Claude Code 自带的 `/doctor prompt-audit`，这里不重做：

- 它是单独的一批，排在第 6 步之后：前面的改动已经封存、用户看过效果，再问他要不要做这一项。
- 报告写「能」：调用它（Skill 工具，`doctor`，参数 `prompt-audit`）。它会先出报告、等用户确认才改；让它动手之前，把它要改的文件另做一次 `slim backup`，它改完再 `slim seal`。这样它的改动可以单独退回。调用失败就请用户自己敲 `/doctor prompt-audit`。
- 报告写「现在不能」或「不确定」：用户的设置保持原样。它背后就是一份官方说明文件，直接读它、照它一步步做。报告给了本机副本的路径和文件日期；没有副本，或副本日期早于三个月，读报告里的原文地址。只有 Codex 时同样处理，对象是 AGENTS.md 和 Codex 的 skill。
- 照官方文件做时，范围先和用户定（它的 Step 0）：默认从每个会话都加载的全局规则文件开始，要不要扩到全部 skill 由用户决定。

### Skill（Claude Code）

模型每次都会收到一份清单：每个 skill 一行，名字加描述。四种处理，都只是在设置里记一笔，**文件一个都不删，随时能改回来**：

| 跟用户怎么说 | 效果 | 适合 |
|---|---|---|
| 保留 | 不动 | 带 ⚠ 的默认选这个 |
| 只留名字 | 模型只看到名字，描述不再占位置 | 偶尔用、名字本身说得清的 |
| 只能手动调 | 模型看不见，用户敲 `/名字` 照样能用 | 平时都是自己敲斜杠调的 |
| 关掉 | 模型看不见，斜杠菜单里也收起来；想用时改回来 | 确定不用的。相当于归档 |

报告已经按用法把模型看得见的 skill 分成五组，按组问，不用一个个过：

- **A 组**（一次没用，也找不到留着的理由）：整组一起问「关掉，还是改成只能手动调」，让用户点名要留的。组里的完整名单用 `slim show --scan <json> --group A` 取。
- **B 组**（一次没用，但带 ⚠）：默认保留。⚠ 原因相同的合成一句讲（「这 N 个是最近才装的，还看不出用不用」），原因独一份的单独讲。
- **C 组**（只有用户手敲过）：建议整组改成「只能手动调」。
- **D 组**（模型只主动调过一两次）：名字说得清的建议「只留名字」。
- **E 组**（在用）：不动。标了「只在某项目用过」的，可以提议**下沉到项目**：把目录搬到 `<项目>/.claude/skills/`，别的项目里模型就不再看到它。

同一个前缀的一大族 skill（比如同一个服务的十几个工具）还有一种收法：**收成一个入口**。新建一个入口 skill，描述写这一族管什么，正文列出每个成员什么时候用、文件在哪；成员全部「关掉」。模型只看到入口这一行，需要时顺着路径去读成员。这要新建文件，先讲清楚，用户同意才做，新文件的路径也列进备份。

讲效果时用报告「日志实记」那一行（Claude Code 记下的、新会话里实际发给模型的清单）。这份清单有预算上限（上下文窗口的 1%），超了 Claude Code 会从最少用的 skill 开始丢掉描述；清单已经顶到上限时，停用 skill 是给剩下的腾位置，清单不一定变短。报告判断不了有没有顶到上限，所以事先不向用户保证清单会短多少，以改完后新开会话的实测为准。

⚠ 标记各自的含义：

- **被点名引用**：别的 skill、规则文件或 hook 里提到了它。停掉之前先看引用者还用不用。
- **像低频保命项**：发版、回滚、迁移、事故这类，本来就几个月用一次。
- **装了才 N 天**：还没到能下结论的时候。
- **软链断了**：入口还在，指向的目录已经不存在，这个 skill 用不了。告诉用户它原本指向哪，由他决定删掉这条软链还是把目标找回来；删由用户自己动手。
- **skillUsage 记着用过，日志里没数到**：两个数据源对不上，按「用过」处理。

「Codex 读」大于 0 的 skill，Codex 是直接按路径读文件的：改 Claude Code 这边的状态不影响它，搬走会让它读不到。软链的 skill 只改状态，位置留在原处。「已经 off 但还在被手敲」的，提一句让用户知道。

**Codex 自己的 skill**：没被读过的候选，选项是保留，或在 `~/.codex/config.toml` 的 `skills.config` 里加一条 `enabled = false`（文件不动）。

### MCP 和工具

开局部分的「MCP 工具说明」按 server 列了大小：这是每句话都带着的工具说明书。

- **Claude Code**：用户级 MCP 存在 `~/.claude.json`，那是 Claude Code 自己随时在写的状态文件，本工具只读。要移除就把命令给用户自己跑：先 `claude mcp get <名字>` 把配置存下来，再 `claude mcp remove <名字> -s user`。讲清楚这一步不在备份保护里。
- **Codex**：0 调用的 server 可以设 `mcp_servers.<名字>.enabled = false`。想进一步收窄的，用 `enabled_tools` 只放行用到的那几个；报告列了近 30 天用到哪些工具，这个 server 一共暴露多少工具脚本不知道，要问用户。
- 开局部分出现了「MCP 工具说明」，说明这些工具的说明书是整份常驻的。Claude Code 默认是用到才加载；常驻的原因看报告「开关」一节：`ENABLE_TOOL_SEARCH` 被设成了 false，或某个 MCP 设了 alwaysLoad。这是取舍：告诉用户它意味着工具说明每轮都带着，连同调用次数一起，让他判断值不值。要改回默认，用 `slim set` 删掉那个环境变量。
- 用户装了功能重叠的工具时，被替代的那个也是候选。

## 4. 配置：不删东西，只改几个设置

同样只记不改。报告的配置部分每一块都有实测数字和一句「怎么读」，照着讲。

### 自动压缩窗口

跟用户说：对话聊到多长，Claude Code 就自动把前面的内容压成一份摘要。窗口设小，每句话带的历史就短；代价是更早变成摘要，细节要回日志里翻。

- 摆报告里的数：每一档上下文长度以上发出去了多少请求、多少 token，有多少个会话长到过那么大。
- 从报告的档位里挑两三个，加上「不改」，每个说清对应哪一行数字，让他选。
- 改法：`settings.json` 的 `autoCompactWindow`，取值 100000 到 1000000。报告写着环境变量 `CLAUDE_CODE_AUTO_COMPACT_WINDOW` 已经设了的，改环境变量那一项（`["env","CLAUDE_CODE_AUTO_COMPACT_WINDOW"]`），因为它优先。
- 可选的一句规则。压缩之后模型手里只有摘要，容易当成全部。用户愿意的话，在全局规则文件里加一句（给他看 diff）：「上下文被压缩之后，你手里的是摘要。继续干活前，缺的细节回会话日志或任务记录里找。」

### 缓存：放着不动再回来

跟用户说：对话历史有缓存，命中时便宜；放久了缓存过期，回来的第一句话要把整段历史按全价重算。报告里「整段重算」的次数和 token 就是这笔钱。这里没有设置可改，给他三个习惯：

- 要离开一阵子，走之前先 `/compact`。
- 隔了很久回来，历史又很长：新开一个会话接着干，比在旧会话里说话便宜。
- 一定要在旧会话里继续、缓存又已经过期时：先切到便宜的模型，`/compact`，再切回来。缓存过期后，压缩要把整段历史重新写一遍缓存，这一步按压缩所用模型的价格算；缓存还热时主模型读自己的缓存本来就便宜，切换省不了多少，摘要写得长时还可能更贵。便宜的那个模型要装得下这段历史。这个做法只验证过计费记在哪个模型名下，跟用户说是可以试的做法，不报省多少。
- 压缩压不掉开局那一块：规则文件和 skill 清单在压缩后照样带着。开局大的，先做第 3 步的清理。

### 子代理用什么模型

报告列了主会话和子代理各用了哪个模型多少次，以及派子代理时有多少次没指定模型。没指定的跟主会话用同一个模型。两种改法，可以都做：

- 设环境变量 `CLAUDE_CODE_SUBAGENT_MODEL`（比如 `sonnet`）：没另外指定模型的子代理默认用它。
- 在全局规则文件里加一张**模型分工表**（给用户看 diff，由他改成自己的分法）。例：「派子代理时每次写明模型。查资料、搜文件、读日志、整理摘要用便宜的模型；写代码、做审查用主力模型；最难的设计问题才用最贵的。」模型名换成用户实际在用的。

### 开关

- 「确定写错或不生效的」：逐条讲清楚错在哪，给出改法。
- 「值得和用户过一遍的几个」（报告里带 `?` 的）：一个一个讲。每个都有一句现成的白话说明，照它讲，再说现在的值，问他要不要改。
- 其余取舍项：报告只列事实。用户问到某个键，或者说了他想要的效果，再去 `references/switches.json` 查那个键管什么、默认是什么、出处在哪。清单开头的 `verified` 是核对日期，超过三个月时，先打开那个键的出处核对再回答。

## 5. 执行

把改动清单完整复述一遍，规则文件的改动在清单里直接写成 diff。用户确认整份清单之后才动手，确认过的 diff 不用再问第二遍：

1. **备份**：`slim backup --paths <这次要动的每个路径>`。要新建的路径（搬出去的新文件、入口 skill、skill 下沉的目的地）也列进去。HOME 之外的项目目录加 `--root <项目目录>`。记下输出的备份 ID。
2. **改**：
   - skill 的状态用 `slim skills`，一次改一整组或点名的一批。
   - `settings.json`、`config.toml` 里的其他键用 `slim set`，多个键写进一个文件用 `--many` 一次改完。这两个文件里常有凭据，全程通过脚本操作，不打开全文。
   - 搬目录用 `slim move --backup <ID> --src <原路径> --dst <搬过去之后的完整路径>`。`--dst` 写到最后那一级名字（`<项目>/.claude/skills/<skill 名>`），两个路径都要在第 1 步的备份里。
   - Markdown 规则文件直接编辑。
3. **封存**：`slim seal --backup <ID>`。
4. **核对**：`slim status --scan <第 1 步的 json>`。
5. **重扫**：再跑一次 `slim scan`（只读），拿改完之后的数字。这时会变的是「模型每轮能看到 N 个」、规则文件的字符数、各项设置的当前值；开局部分和「日志实记」要等用户新开会话才变（第 6 步）。

做完的标准：`seal` 列出的每个文件都在清单里，`status` 里没有 ✗。要逐个键核对（比如哪些 skill 被改了），看 `slim list`。出现 ✗ 表示有文件没备份就被改了，立刻告诉用户是哪个。

```
slim skills --backup ID --state off    --scan <json> --group A --exclude 要留的名字 另一个
slim skills --backup ID --state manual --scan <json> --group C
slim skills --backup ID --state name   名字一 名字二
slim set --backup ID --file ~/.claude/settings.json --path '["autoCompactWindow"]' --value 500000
slim set --backup ID --file ~/.claude/settings.json --path '["skillOverrides","claude-api"]' --delete
slim set --backup ID --file ~/.claude/settings.json --many <文件>
slim set --backup ID --file ~/.codex/config.toml --path '["mcp_servers","playwright","enabled"]' --value false
slim set --backup ID --file ~/.codex/config.toml --path '["skills","config",{"path":"/绝对路径/SKILL.md"},"enabled"]' --value false
```

`--state` 取 `off`（关掉）、`manual`（只能手动调）、`name`（只留名字）、`on`（保留）。`--path` 是 JSON 数组，`--value` 是 JSON 值。`--many` 的文件是一个 JSON 数组，每项 `{"path": [...], "value": ...}` 或 `{"path": [...], "delete": true}`，有一项被拒就整批不改。

`slim set` 拒绝时会说原因（多行值、内联表、带注释的 JSON、手工排版的 JSON、CRLF 和 LF 混用、文件不是 UTF-8）。这些拒绝是有意的：脚本保证不了目标键以外的字节不变时就不改。那种情况只读目标键附近的几行，手动改，改动仍在备份保护内。

## 6. 让用户看到效果

改动在**新开的会话**里才生效，当前这个会话里的数字不会变。告诉用户四件事：

1. 改了什么，用两次扫描的数字说（「模型看得见的 skill 从 A 个变成 B 个」「每个会话都加载的规则文件从 X 字符变成 Y 字符」）。
2. 怎么亲眼看：请用户在平时干活的目录新开一个会话，随便说一句话，回来告诉你。你再扫一次（`slim scan --json <新的 json>`），然后跑 `slim compare --before <第 1 步的 json> --after <新的 json>`，把输出原样给用户：它是两次新开会话第一次请求的实测 token，外加各部分大小的变化。用户还没新开会话时 `compare` 会直接说，照它说的请用户去开。也可以在新会话里敲 `/context`。
3. 备份留着。用几天觉得哪里不顺手，随时可以退回。
4. 回滚命令是什么。

## 7. 回滚

用户想退回：`slim rollback --backup <ID>`，不给 ID 就退最近一次。有多个备份时从新到旧退。

输出以「停：」开头，说明那些文件在我们改完之后又被动过，此时什么都没还原。规则文件的差异脚本会直接打印出来；把文件名和后来多出的改动告诉用户，由他决定要不要加 `--force`。加了 `--force` 之后，被替换下来的版本存在输出里写的那个目录。把这个目录的路径告诉用户，他想留下的后加内容由他自己打开对照、补回去；备份目录里的文件你不读。

## 边界

- 只读不改：`~/.claude.json`、凭据文件、会话日志、插件目录。
- `~/.save-my-tokens/` 里是原样拷贝，可能含凭据，内容不进对话。
- 没量过的数不报。能说的是日志里记下的用量、可见 skill 的个数、字符数、删了几条重复规则。字符数只用来排先后，不折成 token 报给用户。
